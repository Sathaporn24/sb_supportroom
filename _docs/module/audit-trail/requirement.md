## Overview

ทุกวันนี้ถ้ามีข้อมูลในระบบเปลี่ยนไปในทางที่ไม่ควรเป็น ทีม dev หลังบ้านสืบไม่ได้ว่าใครทำ —
รู้ได้แค่ว่า "คนล่าสุดที่แตะแถวนี้คือใคร" ซึ่งมักไม่ใช่คนที่ก่อเรื่อง โมดูลนี้เพิ่ม**บันทึกดิบของทุก
การกระทำเรียงตามเวลา** ลง database เพื่อให้ dev เปิด `SELECT` ไล่ดูเองได้ว่าใครทำอะไรกับข้อมูล
ชุดไหนเมื่อไหร่ ครบทุกครั้ง ไม่ใช่แค่ครั้งล่าสุด

**ความต้องการวันนี้เล็กโดยตั้งใจ** — คำพูดของเจ้าของโปรเจกต์เอง:

> "แค่เป็น log ดิบๆ ก็ได้ ให้ทีม dev หลังบ้านหาตัวการ ดูประวัติผ่าน db ได้ก็พอ"

ไม่ต้องมีหน้าจอ ไม่ต้องมี dashboard ในรอบนี้ แต่**รูปร่างข้อมูลต้องไม่ปิดทางทำ dashboard ทีหลัง**
(ดู R5) — เจ้าของสั่งไว้ในคำขอเดียวกันว่า "ให้พร้อมทำแดชบอร์ดในอนาคตไปด้วยเลย"

## Target Users & Roles

โมดูลนี้**ไม่เพิ่ม role ใหม่** ใช้ 3 ระดับเดิมของ `AdminUser.Role`:

| ผู้ใช้ | ใช้โมดูลนี้ยังไง (รอบนี้) | ใช้ยังไง (อนาคต ถ้าทำ dashboard) |
|---|---|---|
| **ทีม dev หลังบ้าน** (ผู้ใช้จริงเพียงกลุ่มเดียวในรอบนี้) | `SELECT` จาก database ตรงๆ เพื่อสืบว่าใครทำอะไร | — |
| `owner` (School Bright, `CompanyId = null`) | ไม่มีหน้าจอให้ใช้ในรอบนี้ | เห็น log ได้ทุกบริษัท |
| `admin` (ผูกบริษัทเดียว) | ไม่มีหน้าจอให้ใช้ในรอบนี้ | เห็นเฉพาะ log ของบริษัทตัวเอง (R3) |
| `cs` | ไม่มีหน้าจอให้ใช้ในรอบนี้ | ยังไม่เคาะว่าจะเห็นหรือไม่ — ดู OQ-4 |

**ผู้ใช้ที่ถูกบันทึก ≠ ผู้ใช้ที่อ่านบันทึก** — คนที่ถูกบันทึกคือ `AdminUser` (owner/admin/cs)
ที่ลงมือทำให้ข้อมูลเปลี่ยน **ไม่รวมผู้เรียน** (R1.2) ส่วนคนที่อ่านในรอบนี้มีแค่ทีม dev ผ่าน database

## Core Features

### R1 · บันทึกทุกการกระทำที่ admin เป็นผู้ก่อ ครอบคลุมทุก entity (✅ เคาะ 2026-08-27)

ครอบคลุม **create / update / delete ของทุก entity ที่ `AdminUser` (owner/admin/cs) เป็นผู้ก่อ
การกระทำ** — ไม่จำกัด entity ใด entity หนึ่ง ไม่ได้แคบลงเหลือเฉพาะ
`TrainingLink`/`LessonConfig`/`DocumentResource` ตามที่เคยเสนอเป็นทางเลือก

**R1.1** — "delete" หมายรวมถึง soft-delete ที่ระบบนี้ใช้อยู่ (`IsDelete`/`DeletedAt`) ไม่ใช่แค่
การลบจริง เพราะ soft-delete คือรูปแบบการลบปกติของระบบนี้

**R1.2 · ⛔ ไม่รวมกิจกรรมที่ผู้เรียนเป็นผู้ก่อ** (✅ ปิด OQ-1 แล้ว 2026-08-27) — การกระทำที่เกิดจาก
**ผู้เรียน** ไม่ว่าจะสร้างแถวในตารางไหนก็ตาม **อยู่นอกขอบเขตโมดูลนี้** เช่น `LearningSession`
(เกิดตอนผู้เรียนกดเข้าลิงก์และระบุชื่อ) และ `SessionQuestion` (เกิดตอนผู้เรียนถามคำถาม)

**เส้นแบ่งคือ "ใครลงมือ" ไม่ใช่ "ตารางไหน"** — entity หนึ่งอาจถูกแตะได้ทั้งจาก admin และจากผู้เรียน
สิ่งที่บันทึกคือครั้งที่ **`AdminUser` เป็นผู้ก่อ** เท่านั้น · เจ้าของโปรเจกต์ยืนยันว่านี่คือเจตนา
ตั้งแต่แรก (คำขอตั้งต้นเขียนว่า "admin-side actions") ไม่ใช่การตัดขอบเขตลงทีหลัง

### R2 · ความละเอียดระดับ "ใคร ทำอะไร กับแถวไหน เมื่อไหร่" — ไม่เก็บค่าก่อน/หลัง (✅ เคาะ 2026-08-27)

หนึ่งแถว log ตอบได้แค่สี่อย่าง: **ใคร** ทำ **อะไร** กับ **ข้อมูลชุดไหน** **เมื่อไหร่**

**ไม่เก็บ diff ของค่าที่เปลี่ยน** (ไม่เก็บทั้งค่าเดิมและค่าใหม่) — เจ้าของขอความเห็นและรับข้อเสนอนี้
ด้วยเหตุผลสามข้อ:

1. การเก็บ diff ทวีความพยายามขึ้นอีกชั้น บนขอบเขตที่กว้างสุดอยู่แล้ว ("ทุก entity ทุกการกระทำ")
2. ไม่ตรงกับความต้องการที่เจ้าของบอกเอง — ต้องการ**สืบหาตัวการ** ไม่ใช่**กู้ข้อมูลกลับ**
3. เพิ่มทีหลังเฉพาะ entity ที่พบว่าจำเป็นจริงได้ — เริ่มง่ายแล้วขยายถูกกว่าเริ่มซับซ้อนแล้วพบว่าเกินจำเป็น

**ผลที่ต้องรับ และเจ้าของรับแล้ว:** log นี้**ตอบไม่ได้ว่า "ค่าเปลี่ยนจากอะไรเป็นอะไร"** ตอบได้แค่
"คนนี้แก้แถวนี้ตอนนี้" — ถ้าวันหนึ่งต้องการกู้ค่าเดิมกลับ log นี้ช่วยไม่ได้ ต้องพึ่ง database backup

### R3 · แยกตามบริษัท เหมือนทุกตารางในระบบ multi-tenant นี้ (✅ เคาะ 2026-08-27)

log ผูกกับบริษัท (`CompanyId`) เหมือนข้อมูลอื่นทั้งระบบ · `owner`/`admin` ของบริษัทหนึ่ง
ต้องไม่มีทางเห็นแถว log ของบริษัทอื่นเลย

**R3.1** — เจตนาที่ตามมาจาก R3: แถว log ควรผูกกับ**บริษัทของข้อมูลที่ถูกกระทำ** ไม่ใช่บริษัทของ
คนที่ลงมือ (มิฉะนั้น owner ที่ `CompanyId = null` จะทำให้ log ตกไปอยู่นอกบริษัทใดๆ และบริษัท
เจ้าของข้อมูลจะมองไม่เห็นการกระทำที่เกิดกับข้อมูลตัวเอง) · เคสขอบที่ยังไม่ปิด — ดู **OQ-2**

### R4 · เก็บถาวร ไม่มีนโยบายลบทิ้ง (✅ เคาะ 2026-08-27)

ไม่กำหนด retention / ไม่มี cleanup job ในรอบนี้ เหตุผลที่เลื่อนได้โดยไม่เสียหาย:

- การเพิ่ม retention job ทีหลังเป็น**การเพิ่มล้วนๆ ไม่ต้องแก้ schema** และใช้รูปแบบ worker เดิม
  ที่โมดูลนี้เคยใช้กับ `lesson_purge` อยู่แล้ว
- ปริมาณต่ำ เพราะเป็นการกระทำของ admin/cs/owner ไม่ใช่กิจกรรมของผู้เรียน — **ข้อนี้นิ่งแล้ว**
  ตั้งแต่ปิด OQ-1 (R1.2 ตัดกิจกรรมผู้เรียนออกนอกขอบเขตชัดเจน) ไม่ใช่สมมติฐานที่ยังรอคำตอบอีกต่อไป

### R5 · รูปร่างข้อมูลต้องขยายได้ทีหลัง — แต่ไม่ต้องนิ่งวันนี้ (✅ เคาะ 2026-08-27)

"พร้อมทำ dashboard" **แปลว่า "อย่าออกแบบจนตีบตัน" ไม่ได้แปลว่า "ต้องนิยาม action ทุกชนิดให้ครบ
ตั้งแต่วันนี้"** — เจ้าของยืนยันว่า**ไม่ต้องมี `ActionType` enum/รายการตายตัวในรอบนี้** ขอแค่
รูปร่างข้อมูลที่เพิ่มชนิดใหม่เข้าไปทีหลังได้โดยไม่ต้องรื้อ

**R5.1 · ข้อนี้เป็นข้อจำกัดเรื่องรูปร่างข้อมูล ไม่ใช่ใบอนุญาตสร้าง dashboard** — ห้ามให้คำว่า
"พร้อมทำ dashboard" ขยายขอบเขตรอบนี้ไปเป็นการสร้าง UI จริง dashboard เป็นงานอนาคตที่ชัดเจน
(ดู `## Scope` → Later)

### R6 · ไม่มี UI ในรอบนี้ ใช้งานผ่าน database ตรงๆ (✅ เคาะ 2026-08-27)

รอบนี้ส่งมอบแค่**ข้อมูลที่ทนทานและ query ได้** ไม่มีหน้าจอ ไม่มี endpoint สำหรับดู log
ไม่มีรายงาน — ทีม dev เปิด `SELECT` เองพอ

## Scope

### MVP (must-have)

1. **R1** — บันทึก create/update/delete ของทุก entity **เฉพาะครั้งที่ `AdminUser` เป็นผู้ก่อ**
   (ไม่รวมกิจกรรมผู้เรียน ตาม R1.2)
2. **R2** — ความละเอียดระดับ "ใคร/อะไร/แถวไหน/เมื่อไหร่" ไม่มี diff
3. **R3** — แยกตามบริษัท
4. **R5** — รูปร่างข้อมูลที่ขยายชนิด action ได้ทีหลัง

### Later (nice-to-have)

- **หน้า dashboard / UI ดู log** — ชัดเจนว่าเป็นงานอนาคต ไม่ใช่รอบนี้ (R5.1, R6)
- **endpoint / API สำหรับอ่าน log** — ยังไม่ต้องมี รอบนี้อ่านผ่าน database
- **เก็บค่าก่อน/หลัง (diff)** เฉพาะ entity ที่พบว่าจำเป็นจริง — ตกลงกันแล้วว่าเพิ่มทีหลังได้ (R2)
- **นโยบาย retention / cleanup job** — เลื่อนไว้โดยตั้งใจ (R4)
- **การแจ้งเตือนเชิงรุกเมื่อเจอ action น่าสงสัย** — ไม่ได้ร้องขอ ไม่อยู่ในรอบนี้

### รอบปิด scope — ยืนยัน 2026-08-27

ถามครบตามขั้นตอนปิด scope ก่อนส่ง `system-analyst` แล้ว เจ้าของยืนยันว่า**ปิดตรงที่คุยกันพอดี**:
log ดิบทุก entity ทุก action **ที่ admin เป็นผู้ก่อ** · ไม่มี diff · เก็บถาวร · แยกตามบริษัท ·
**ไม่มีอย่างอื่นเพิ่ม**

### Pre-existing assets reconciled

ไม่มี schema/DDL/mockup ที่เตรียมไว้ล่วงหน้าสำหรับโมดูลนี้ — จุดเริ่มคือการตรวจ schema จริงที่มี
อยู่แล้วเพื่อหาช่องว่าง ของเดิมที่เกี่ยวข้องและสถานะในโมดูลนี้:

| ของที่มีอยู่แล้ว | สถานะในโมดูลนี้ |
|---|---|
| คอลัมน์ `CreateBy`/`CreateDate`/`UpdateBy`/`UpdateDate`/`DeleteBy`/`DeletedAt` บนทุก entity (`IEntityMaster`) | **คงไว้ ไม่แตะ ไม่แทนที่** — ทำงานถูกต้องอยู่แล้ว โมดูลนี้เพิ่มของใหม่ข้างๆ |
| soft-delete (`IsDelete`/`DeletedAt`) | **ใช้ต่อ ไม่แก้** — และ "delete" ใน R1 หมายถึง soft-delete นี้ (R1.1) |
| `AdminUser.LastLoginAt` | **คงไว้ ไม่แตะ** — ไม่ถูกแทนที่ด้วยประวัติ login เว้นแต่ **OQ-4** ปิดว่าให้เก็บ login event |
| `ILogger<T>` (log ลงไฟล์/console) | **คนละชั้น ไม่เกี่ยวกัน** — ไม่ใช่สิ่งที่โมดูลนี้มาแทน |
| รูปแบบ background worker ที่ใช้กับ `lesson_purge` | **ยังไม่ใช้ในรอบนี้** — อ้างถึงเป็นเหตุผลว่าทำไม retention เลื่อนได้ (R4) |
