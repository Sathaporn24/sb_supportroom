# Requirement — Knowledge Base & Teaching Content Intake

**โมดูล:** `knowledge-base` · **สถานะ:** R1–R9 เคาะครบ · **CR-2 (R4.6), CR-3 (R4.7)
และ CR-4 (R9) เพิ่มใหม่ 2026-08-26 · พร้อมส่ง `system-analyst` (amend)**
**ที่มา:** เจ้าของโปรเจกต์ยกประเด็นเมื่อ 2026-08-18 ว่าภาพรวมระบบ "ยังไม่ครบวงจร" —
ครึ่งซ้ายของวงจร (เตรียมความรู้ → แจกลิงก์ → เรียน → จับคำถาม) ทำงานได้แล้ว แต่ครึ่งขวา
(รีวิว → แก้ความรู้ → รู้ว่าดีขึ้น) ตัน

> เอกสารนี้เก็บ **ความต้องการทางธุรกิจ** ไม่ใช่วิธีทำ · `docs/KNOWLEDGE_ROADMAP.md` ที่มีอยู่แล้ว
> เป็น roadmap เชิงเทคนิคของ retrieval/eval — คนละชั้นกับเอกสารนี้ ไม่ทับกัน อ่านคู่กันได้

## Requirement ที่เจ้าของโปรเจกต์เคาะแล้ว

### R1 · Taxonomy 3 ชั้น (✅ เคาะ 2026-08-19)

`category > subcategory > ชื่อเนื้อหา` ใช้กับ **ทั้งบทเรียนและเอกสาร** ทำหน้าที่สองอย่างพร้อมกัน:
จัดเก็บให้เป็นระเบียบตั้งแต่ตอนนำเข้า และเป็นเมนูค้นหา (คล้าย sidebar/megamenu) ตอนต้องหา
บทเรียน/สื่อการสอน/เทรนนิ่ง

**R1.1 · หนึ่งบทเรียนอยู่ได้หมวดเดียว และต้องมีหมวดเสมอ** (✅ เคาะ 2026-08-19) —
เหมือนไฟล์ในโฟลเดอร์ ไม่ใช่ป้ายกำกับ · ทำให้เมนูชัดและความรู้ระดับหมวด (R3) ไม่กำกวม
**ผลที่ต้องรับ:** บทเรียนที่คร่อมสองหมวดจริง ๆ ต้องเลือกข้างเดียว และ**ข้อมูลเดิมที่มีอยู่แล้ว
ต้องถูกจัดหมวดให้ครบก่อนเปิดใช้ฟีเจอร์นี้**

**R1.2 · ลบหมวดที่ยังมีบทเรียนหรือเอกสารอยู่ไม่ได้** (อนุมานจาก R1.1 — ยังไม่ได้ยืนยันตรง ๆ) —
เพราะบทเรียนต้องมีหมวดเสมอ การลบหมวดจึงต้องบล็อกไว้จนกว่าจะย้ายของออกหมด

### R2 · แต่ละบริษัทจัดหมวดของตัวเอง (✅ เคาะ 2026-08-19)

admin/cs ของบริษัทสร้างและแก้หมวดของตัวเองได้ **ไม่ใช่** School Bright กำหนดชุดกลาง —
เข้ากันกับโครงข้อมูลเดิมที่ทุกอย่างแยกตามบริษัทด้วย `CompanyId` + query filter

**ผลข้างเคียงที่ยอมรับแล้ว:** ทุกบริษัทต้องตั้งหมวดเองตั้งแต่เริ่มใช้งาน · หมวดไม่เหมือนกัน
ข้ามบริษัท ทำให้รายงานเทียบข้ามบริษัท ("หมวดการเงินมีปัญหาบ่อยสุดทุกบริษัท") ทำไม่ได้ในเฟสนี้

### R3 · คลังความรู้ 3 ระดับ (✅ เคาะ 2026-08-19)

บทเรียน / **หมวด** / ทั้งบริษัท — เอกสารที่วางระดับหมวดต้องตอบได้ทุกบทเรียนในหมวดนั้น
แต่ไม่โผล่ไปหมวดอื่น · ปัจจุบันมีแค่ระดับบนสุดกับล่างสุด

**ต้องรู้:** ทุกคำถามยิงทุก namespace พร้อมกัน การเพิ่มระดับที่สามคือ query ที่เพิ่มขึ้นต่อคำถาม

**R3.1 · ย้ายบทเรียนข้ามหมวด = ความรู้ที่ใช้ตอบเปลี่ยนตามหมวดใหม่ทันที และต้องเตือนก่อนย้าย**
(✅ เคาะ 2026-08-19) — บทเรียนจะเลิกเข้าถึงเอกสารระดับหมวดเดิมและเริ่มเข้าถึงของหมวดใหม่
ทันทีที่ย้าย ซึ่งแปลว่า **คำตอบของ AI สำหรับบทเรียนนั้นเปลี่ยนทันทีโดยไม่มีใครสั่งโดยตรง** ·
ตอนกดย้ายต้องบอกให้ชัดว่าจะเลิกใช้เอกสารกี่ชิ้นและจะเริ่มใช้ของหมวดใหม่แทน แล้วให้ยืนยัน

### R4 · ขาเข้าสื่อการสอน — บทพูดที่แก้ได้ (✅ เคาะ 2026-08-19)

**แยกทางเดินตาม `ContentSourceType` ชัดเจน:**

| แหล่ง | บทพูดมาจาก | แก้ที่ไหน |
|---|---|---|
| `google_slides` | Speaker Notes | **แก้ที่ Google Slides ตามปกติ ไม่มีช่องแก้ในระบบ** — ทีม School Bright สร้างเด็คเองทุกเด็คและแก้ได้ จึงไม่ต้องมีบทพูดสองที่ให้สับสน (สอดคล้องกฎสถาปัตยกรรมข้อ 8) |
| `pdf` | ข้อความบนหน้า | **มีช่องบทพูดต่อหน้าในระบบ** prefill ด้วยข้อความที่ระบบดึงได้ CS แก้ทับได้ |

กติกาของช่องบทพูด PDF:
1. **เก็บเฉพาะหน้าที่ CS แก้จริง** — ห้ามเซฟข้อความ prefill ของหน้าที่ไม่ได้แตะลงฐานข้อมูล
   ไม่งั้นเป็นการแช่แข็งสำเนาที่พังไว้ถาวร และการปรับตัวแปลงให้ดีขึ้นวันหลังจะไม่มีผลกับหน้าเหล่านั้น
2. **มีค่าที่แก้ไว้ = ใช้ค่านั้นเสมอ** ไม่มีค่า = ใช้ข้อความที่ดึงจากไฟล์
3. **อัปโหลด PDF ใหม่ = ล้างบทพูดที่แก้ไว้ทั้งหมด** ต้องเตือนจำนวนหน้าที่จะถูกลบและให้ยืนยันก่อน
   (เหตุผล: id ต่อหน้าของ PDF คือ `pdf-page-N` ผูกกับเลขหน้าล้วน แทรกหน้าใหม่ 1 หน้า
   บทพูดทุกหน้าถัดไปจะเลื่อนผิดโดยไม่มี error — ล้างทิ้งชัดเจนกว่าเดาว่าหน้าไหนคือหน้าไหน)
4. **PDF สแกนที่ดึงข้อความไม่ได้เลย → เตือนชัดว่าเป็นไฟล์สแกน ต้องพิมพ์บทพูดเองทุกหน้า**
   ไม่ทำ OCR ในเฟสนี้ · ข้อเท็จจริงวันนี้ (ตรวจโค้ดแล้ว 2026-08-19): ฝั่ง **คลังความรู้** จับได้
   อยู่แล้ว — ได้ 0 chunk จะตั้งสถานะเป็น `failed` ไม่ได้ขึ้นว่าสำเร็จ · แต่ฝั่ง **บทพูด** ไม่มีใคร
   ตรวจเลย ไฟล์สแกนจะได้บทพูดว่างทุกหน้าแล้วห้องเรียนก็เงียบ โดยไม่มีอะไรเตือน CS ก่อนถึงหน้างาน
5. **บทพูดที่แก้แล้วต้องมีผลกับคำตอบของ AI ด้วย** — สิ่งที่ AI พูดกับสิ่งที่ AI ใช้ตอบต้องเป็น
   เรื่องเดียวกัน ดังนั้นแก้บทพูดแล้วต้อง re-index หน้านั้น (chunk id ผูกกับหน้าอยู่แล้ว
   จึง upsert เฉพาะหน้าที่แก้ได้ ไม่ต้อง re-embed ทั้งเด็ค)

**ข้อเท็จจริงที่ต้องแก้ไปพร้อมกัน:** วันนี้บทเรียน PDF ใช้ข้อความจากไฟล์เดียวกันสองเส้นทาง
คนละตัวแปลง — บทพูดมาจาก `PdfSlidesRenderer` (เก็บหน้าว่างไว้) ส่วนคำตอบมาจาก
`PdfTextExtractor` ผ่านเอกสารแนบ (ตัดหน้าว่าง) และบทเรียน PDF ไม่เคยถูก index เข้า namespace
ของบทเรียนตัวเองเลย (`ILessonConfigService` index เฉพาะบทที่มี `presentationId`)

### R4.6 · เฟสจัดการเนื้อหาก่อนสร้างบทเรียน PDF (✅ เคาะครบ 2026-08-26 · ที่มา CR-2)

**คำพูดของเจ้าของโปรเจกต์:** *"ต้องมียืนยันการสร้างปิด job ตอนท้าย"* ·
*"บทพูดคือตัวขยายความสำคัญ"*

> **ต้นเรื่อง (ตรวจโค้ดจริงก่อนเขียน 2026-08-26 ที่ `frontend/src/components/admin/LessonForm.tsx`
> `handlePdfUpload` บรรทัด 186–221):** วันนี้ในหน้า **สร้างบทเรียนใหม่** แค่ *เลือกไฟล์* PDF
> ก็เกิดผลถาวรทันทีก่อนกด "สร้าง" แม้แต่ครั้งเดียว — `api.uploadDocument` อัปไฟล์ขึ้น storage
> และสร้างแถว `DocumentResource` scope `company` จริง (คอมเมนต์ในโค้ดบรรทัด 190–191 เขียน
> เหตุผลไว้เองว่าโหมดสร้างยังไม่มี lesson id) เอกสารนั้น**เข้าคลังความรู้และถูก index จริง** ·
> ถ้า CS ทิ้งฟอร์มไปโดยไม่กด "สร้าง" ไฟล์นั้นกลายเป็น **orphan ถาวร** ที่ scope `company`
> ไม่มีบทเรียนผูก และปนอยู่ในหน้าคลังรวม (`/admin/documents`) โดยไม่มีอะไรบอกว่ามันคือเศษ draft

**เหตุผลเชิงเนื้อหาที่ต้องมีเฟสรีวิว (เจ้าของโปรเจกต์ใช้ระบบจริงแล้วพบเอง):** ข้อความที่ดึงจาก PDF
ได้ตรง ๆ **พูดออกเสียงตามนั้นไม่ได้** — บางหน้าได้เนื้อหาทั้งหน้าซึ่งละเอียดเกินจังหวะการพูด
บางหน้าเป็นรูปเกือบทั้งหน้ามีข้อความสั้น ๆ แค่ป้ายกำกับ/ตัวอย่าง ซึ่งบทพูดต้อง **ขยายความ**
สิ่งที่อยู่บนสไลด์ ไม่ใช่อ่านซ้ำ · **ข้อความที่ดึงได้คือร่างตั้งต้น ไม่ใช่บทพูดที่เสร็จแล้ว**
CS จึงต้องมีจังหวะแก้ก่อนบทเรียนขึ้นใช้จริง

### R4.7 · ตัดหน้าออกจากบทเรียน PDF (✅ เคาะครบ 2026-08-26 · ที่มา CR-3)

**คำพูดของเจ้าของโปรเจกต์ (เหตุผลตั้งต้น):** *"เปิดโอกาสให้ปรับปรุง แก้ไข ตัดเนื้อหาที่ไม่จำเป็นได้"*

> **⚠️ นี่คือความต้องการเชิงบรรณาธิการทั่วไป ไม่ใช่ทางเลี่ยงของปัญหาแปลงไฟล์เสีย** —

### R5 · คลังความรู้เป็น Q&A ที่โตจากคำถามจริง (✅ เคาะ 2026-08-19)

**แนวคิดหลักมาจากเจ้าของโปรเจกต์: คลังความรู้คือคู่ถาม-ตอบ ไม่ใช่เอกสารอย่างเดียว**
"ถามประมาณไหน ตอบประมาณนั้น — พอผู้ใช้ถามมาประมาณไหน ก็เอาคำตอบประมาณนั้นไปตอบ"

สิ่งนี้เปลี่ยนวิธีปิดวงจร: เดิม CS กด "ตอบผิด" แล้วต้องไปเขียนเอกสารใหม่ → อัปโหลด → รอ index
ซึ่งขั้นตอนเยอะจนไม่มีใครทำจริง · ใหม่คือ **CS เขียนคำตอบที่ถูกลงไปตรงจุดที่เจอปัญหาเลย**

**R5.1 · คิวงาน = คำถามที่ยังไม่มีคำตอบที่ถูก — มาจากสองแหล่ง ต้องแยกให้เห็นว่ามาจากไหน**

| แหล่ง | เกิดเมื่อ | ต้นทุน |
|---|---|---|
| `answerStatus = not_found` | AI รู้ตัวเองว่าไม่มีข้อมูล — เข้าคิว**อัตโนมัติ** | ฟรี ไม่ต้องมีคนอ่าน · น่าจะเป็นปริมาณหลัก |
| CS กด "ตอบผิด" | คนอ่านย้อนหลังแล้วพบว่า AI มั่นใจแต่ตอบผิด | ใช้เวลาคน · แต่จับสิ่งที่แหล่งแรกจับไม่ได้เลย |

วันนี้ทั้งสองแหล่งกระจายอยู่ในหน้าสรุปของแต่ละการเรียน — ลิงก์เดียวมีผู้เรียน 40 คน ต้องเปิดดู
40 หน้าถึงจะรู้ว่ามีคำถามอะไรที่ตอบไม่ได้ · **ต้องมีหน้าเดียวที่รวมข้ามการเรียนและข้ามบทเรียน**

**R5.2 · การปิดงานเกิดเอง ไม่ต้องมีปุ่ม "แก้แล้ว"** — คำถามที่มีคำตอบที่ถูกแล้วคือคำถามที่ออกจากคิว
ไม่มีสถานะ workflow แยก ไม่มีการส่งงานต่อไปหาใคร (ผลพลอยได้จากการแก้ตรงจุด)

**R5.3 · AI ใช้ Q&A เป็นหลักฐาน แล้วเรียบเรียงใหม่ ห้ามคัดลอกมาตอบตรง ๆ**
เหตุผล: คำถามที่ใกล้กันมากในเชิงภาษาอาจต่างกันคนละเรื่องในสาระ
("ลบข้อมูลนักเรียนยังไง" กับ "ลบข้อมูลนักเรียนที่จบไปแล้วยังไง") · การเรียบเรียงใหม่ทำให้ AI
ยังปฏิเสธได้เมื่อ Q&A ที่หยิบมาไม่ตรงคำถามจริง ซึ่งการคัดลอกมาวางทำไม่ได้

**R5.4 · CS เลือก scope ตอนบันทึกคำตอบ** — บทเรียนนี้ / ทั้งหมวด / ทั้งบริษัท (ตรงกับ R3)
เพราะคำถามจำนวนมากเป็นเรื่องทั่วไปที่ไม่ผูกกับบทเรียนที่บังเอิญถูกถามตอนนั้น

**R5.5 · เมื่อ Q&A ขัดกับสไลด์/เอกสาร → เอกสารชนะ และต้องยกธงให้คนเห็น**
AI ตอบตามเอกสารไปก่อน **แต่ต้องขึ้นรายการให้ CS เห็นว่า Q&A นี้ขัดกับเอกสาร** เพื่อไปแก้เอกสาร
ที่เป็นต้นเหตุจริง · เหตุผลที่ต้องมีธง: ถ้าเอกสารชนะเงียบ ๆ เคสที่ AI ตีความเอกสารกำกวมผิด
จะแก้ไม่ได้เลยด้วย Q&A และจะตอบผิดซ้ำเรื่อย ๆ โดยไม่มีใครรู้ว่าเอกสารเป็นต้นเหตุ

**ข้อจำกัดที่ต้องยอมรับ:** ลำดับความสำคัญนี้บังคับได้แค่ระดับ prompt (ส่งทั้งเอกสารและ Q&A
เข้าไปพร้อมคำสั่งว่าให้ยึดเอกสารเมื่อขัดกัน) **ไม่ใช่กลไกที่บังคับได้จริงเหมือนโค้ด** และตัว AI
เป็นคนตัดสินเองว่าอะไรคือ "ขัดกัน"

**R5.7 · `cs` เขียนคำตอบแล้วใช้ได้ทันที ไม่ต้องรออนุมัติ** (✅ เคาะ 2026-08-19) —
`cs` คือพนักงานของบริษัทลูกค้าที่ทำงานกับเรื่องนี้ทุกวัน การให้รออนุมัติจะทำให้วงจรที่เพิ่งปิดได้
กลับมาช้าอีก · **ความเสี่ยงที่แลกมา:** คำตอบที่ผิดจะถูกใช้กับครูทุกคนทันที ชดเชยด้วย R5.6
(รู้ว่าใครเขียน เมื่อไหร่ และแก้/ลบได้)

**R5.6 · Q&A ต้องรู้ว่าใครเขียน เขียนเมื่อไหร่ และแก้/ลบได้** — ระบบ School Bright เปลี่ยน
คำตอบที่เขียนไว้เมื่อ 6 เดือนก่อนอาจใช้ไม่ได้แล้ว · ยังไม่ทำวันหมดอายุอัตโนมัติในเฟสนี้

### R6 · ความน่าเชื่อถือของขาเข้าเอกสาร (✅ เคาะ 2026-08-19)

> **บริบท — อัปโหลด 1 ไฟล์มี 5 ขั้น:** (1) เก็บไฟล์ + บันทึก metadata → (2) เข้าคิวรอทำเบื้องหลัง
> → (3) แปลงไฟล์เป็นข้อความทีละหน้า → (4) แปลงข้อความเป็น embedding (เสียเงินจริง) →
> (5) เก็บลง Pinecone รอให้ AI หยิบไปตอบ · R6 แก้ขั้น 2, 3 และ 5

**R6.1 · ลบเอกสาร = soft delete ในฐานข้อมูล + ลบ vector ออกจาก Pinecone จริง**

แยกสองที่ให้ชัด เพราะพฤติกรรมต่างกันโดยสิ้นเชิง:

| | ฐานข้อมูล | Pinecone |
|---|---|---|
| วิธีลบ | **soft delete** (`IsDelete`/`DeletedAt` มีอยู่ในทุก entity แล้ว) กู้คืนได้ | **ลบจริง** |
| ทำไม | เก็บประวัติ กู้คืนได้ ตรงกับแบบแผนของระบบส่วนใหญ่ | ไม่มี query filter แบบฐานข้อมูล · ถ้า vector ยังอยู่ AI ก็ยังหยิบมาตอบ soft delete จึงไม่มีความหมายที่นี่ |

กู้คืนเอกสาร = แปลงและ index ใหม่จากไฟล์ที่ยังอยู่ (ขั้น 3–5 ซ้ำ เสียค่า embedding อีกรอบ
ยอมรับได้) · chunk id เป็น `{documentId}-{chunkId}` อยู่แล้วจึงลบด้วย id prefix ได้ตรง ๆ
**แต่ `IKnowledgeIndexProvider` วันนี้มีแค่ `DeleteNamespaceAsync` (ลบทั้ง namespace)
ต้องเพิ่มความสามารถลบทีละชุด**

**R6.2 · คิวงานเก็บลงฐานข้อมูล และทำงานที่ค้างต่อเองตอนสตาร์ต**

วันนี้คิวอยู่ในหน่วยความจำล้วน (`BackgroundTaskQueue`) — restart เมื่อไหร่งานที่รออยู่หายหมด
เอกสารค้างสถานะ `pending` ตลอดกาลโดยไม่มีใครรู้ · ต้องเก็บงานลง DB และเมื่อระบบสตาร์ตใหม่
ให้ไล่เก็บงานที่ค้างมาทำต่อเอง **ไม่ต้องรอ CS มากดลองใหม่** · ล้มแล้วลองซ้ำได้เอง

**R6.3 · CS เปิดดูข้อความที่แปลงได้ (ขั้น 3) ได้ตลอด ทุกไฟล์ ไม่ใช่เฉพาะตอนล้มเหลว**

เหตุผลที่ต้องดูได้แม้ไฟล์ที่ขึ้นว่าสำเร็จ: ระบบตรวจได้แค่ว่า "ว่างเปล่าหรือไม่" ตรวจไม่ได้ว่า
"เสียหายหรือไม่" — ไฟล์ที่ตัวอักษรไทยเพี้ยน (วรรณยุกต์กลายเป็นอักขระเสีย ตามที่พบจริงในการ
ทดสอบ 2026-08-19) จะแปลงได้ข้อความจำนวนมาก ขึ้นสถานะ `indexed` ตามปกติ ทั้งที่คลังความรู้
เพิ่งรับข้อความเสียเข้าไป · **สายตาคนคือทางเดียวที่จับเคสนี้ได้**

**R6.4 · สถานะล้มเหลวต้องบอกสาเหตุ** — วันนี้ `failed` ครอบทั้งแปลงไฟล์ไม่ได้ / ได้ข้อความเปล่า /
embedding ล่ม ซึ่งวิธีแก้คนละเรื่องกัน (เปลี่ยนไฟล์ / พิมพ์เอง / ลองใหม่) ต้องแยกให้ CS รู้ว่า
ต้องทำอะไรต่อ · ห้ามแสดงรายละเอียดภายในของ provider หรือ error ดิบให้ผู้ใช้เห็น

### R8 · อัปโหลดที่เดียว แต่จัดระเบียบได้ (✅ เคาะครบ 2026-08-24)

**คำพูดของเจ้าของโปรเจกต์:** *"จุดที่ใช้ยากคือ ส่วนที่ต้องอัพโหลดในหน้าเนื้อหานั้น
อยากให้อัพโหลดที่เดียวแต่จัดระเบียบได้"*

> **ข้อเท็จจริงวันนี้ (ตรวจโค้ดแล้ว 2026-08-24):** `DocumentUploadList` ถูกวางไว้ **สองที่**
> คือ `app/admin/documents/page.tsx:22` (โหมด library มีตัวเลือก scope) และ
> `app/admin/lessons/[slug]/page.tsx:448` (ส่ง `fixedScope={{scopeType:"lesson", scopeId}}`
> ล็อก scope ไม่มีตัวเลือก ไม่มี filter ไม่มีปุ่มย้าย ตามที่ DS-8/Q-C ออกแบบไว้)
> **"หน้าเนื้อหานั้น" ที่เจ้าของโปรเจกต์พูดถึง = ตัวที่ฝังในหน้าแก้บทเรียน**

**R8.1 · จุดอัปโหลด "เอกสารประกอบ" เหลือที่เดียว = หน้าคลังรวม · การ์ด "เอกสารประกอบ"
ในหน้าแก้บทเรียนถูกลบทิ้ง** (✅ เคาะ 2026-08-24 · คำตอบ CR-1.j = "ลบทิ้งไปเลย") —
CS ไม่ต้องจำว่า "อัปจากหน้าไหนได้ scope อะไร" · การอัปโหลดแบบผูกกับบทเรียนยัง**เป็นตัวเลือก
ที่ถูกต้องและยังต้องมีต่อไป** (CR-1.f ยืนยันว่า "กลุ่มความรู้" ที่เจ้าของโปรเจกต์หมายถึงคือ
**บทเรียน**) — เปลี่ยนแค่ว่าเลือก scope นั้นจากหน้าคลังรวม ไม่ใช่มีเครื่องอัปโหลดตัวที่สอง
ที่ล็อก scope ไว้แล้วในหน้าแก้บทเรียน · **ผลกับ `design.md`: DS-8/Q-C (โหมด `fixedScope`)
ถูกยกเลิก** — `system-analyst` ต้อง amend contract นั้น ไม่ใช่ให้ engineer ตัดสินเอง

**R8.2 · ห้ามตีความ R8.1 เป็นการเลิกใช้ scope ระดับบทเรียน** — เอกสารที่ผูกกับบทเรียนที่มีอยู่แล้ว
ยังอยู่เหมือนเดิม ไม่ต้องย้าย ไม่ต้อง re-index · R8 เป็นเรื่อง **UI ว่าอัปจากที่ไหน** ล้วน
ไม่ใช่เรื่อง data model หรือ retrieval

**R8.3 · ⛔ ขอบเขตที่ห้ามข้าม: R8.1 ไม่ครอบการอัปโหลด PDF ที่เป็นตัวบทเรียนเอง**

> **พบตอนตรวจโค้ดจริง 2026-08-24 ก่อนเขียนข้อนี้:** หน้าแก้บทเรียนมีการอัปโหลด **สองอย่าง
> ที่คนละเรื่องกันโดยสิ้นเชิง** แต่ใช้ `api.uploadDocument` ตัวเดียวกัน —
> (1) การ์ด **"เอกสารประกอบ"** (`DocumentUploadList` บรรทัด 448) = ความรู้ที่ใช้ตอบคำถาม
> **นี่คือตัวที่ R8.1 สั่งลบ** · (2) `handlePdfUpload` (บรรทัด ~173) = **ไฟล์ PDF ที่เป็นสไลด์
> ของบทเรียนนั้นเอง** ซึ่งอัปแล้วต้องเรียก `previewPdfLessonContent` ต่อทันทีเพื่อสร้าง
> `slideConfigs` และตั้ง `pdfDocumentResourceId` — **ตัวนี้ห้ามแตะ**

เหตุผล: PDF ตัวสไลด์ **ไม่ใช่เอกสารในคลังความรู้** แต่เป็นเนื้อหาของบทเรียน มันต้องอัปจาก
หน้าแก้บทเรียนเพราะผลลัพธ์ของมันคือรายการหน้า/บทพูดของบทเรียนนั้น (ผูกกับ **R4** ทั้งหมด) ·
ถ้าใครอ่าน R8.1 แล้วลบทางนี้ไปด้วย **จะสร้างบทเรียนแบบ PDF ไม่ได้อีกเลย** — ข้อนี้เขียนไว้
เพราะคำว่า "อัปโหลดที่เดียว" อ่านแบบกว้างเกินไปได้ ไม่ใช่เพราะเจ้าของโปรเจกต์เคยขอให้ลบ

> **📌 แก้ไข 2026-08-26 — ขอบเขต "ห้ามแตะ `handlePdfUpload`" ของ R8.3 ถูกแทนที่โดย R4.6
> อย่างเป็นทางการ (เจ้าของโปรเจกต์ยืนยันตรง: "CR นี้แทนที่เจตนา ไม่ใช่การละเมิดขอบเขตเดิม")**
>
> **สิ่งที่ยังมีผลเต็มที่:** เจตนาเดิมของ R8.3 — ทางอัปโหลด **PDF ตัวสไลด์ของบทเรียน**
> ต้องไม่ถูกลบทิ้งไปพร้อมกับการ์ด "เอกสารประกอบ" ตาม R8.1 · การอัปโหลดสองอย่างในหน้าแก้บทเรียน
> ยังคนละเรื่องกันโดยสิ้นเชิงเหมือนเดิม
>
> **สิ่งที่เปลี่ยน:** คำว่า "ห้ามแตะ" เดิมหมายถึง *ห้ามลบทิ้ง* ไม่ใช่ *ห้ามปรับปรุงตลอดกาล* ·
> **R4.6 สั่งแก้พฤติกรรมของ `handlePdfUpload` โดยตรงและโดยเจตนา** (เลิกอัปโหลด/สร้าง
> `DocumentResource` ตอนเลือกไฟล์ ย้ายไปเกิดที่จุดยืนยันแทน ตาม R4.6.1/R4.6.5/R4.6.6) ·
> **`qa-engineer` รอบหลังต้องไม่รายงานการแก้ `handlePdfUpload` ตาม R4.6 ว่าเป็นการละเมิด R8.3** —
> R4.6 คือ requirement ที่ใหม่กว่าและเจ้าของโปรเจกต์เคาะแล้ว · การละเมิด R8.3 ที่ยังนับว่าเป็น
> การละเมิดจริงมีอย่างเดียว คือ **การลบเส้นทางอัป PDF ตัวสไลด์ทิ้งจนสร้างบทเรียน PDF ไม่ได้**

**R8.4 · หน้าแก้บทเรียนต้องยังบอกได้ว่าบทเรียนนี้มีเอกสารอะไรผูกอยู่** — การ์ดที่ถูกลบตาม R8.1
วันนี้เป็นที่เดียวที่ CS เห็นรายการเอกสารของบทเรียนนั้น (และเห็นว่าไฟล์ไหนคือตัวที่ขับสไลด์
ผ่าน `primaryDocumentId`) · ลบแล้วต้องไม่กลายเป็นตาบอด — อย่างน้อยต้องมีทางไปหน้าคลังรวม
แบบกรองมาที่บทเรียนนี้ไว้ให้แล้ว (ต่อกับ **R7.3**) · **ไม่ใช่การเอาเครื่องอัปโหลดกลับมา**

### R9 · ถังบทเรียน กู้คืน และลบถาวร (✅ เคาะครบ 2026-08-26 · ที่มา CR-4)

**ที่มา:** เจ้าของโปรเจกต์ตรวจหน้าจัดการบทเรียนจากระบบจริงแล้วพบว่าแต่ละบทเรียนมีทางเปิด/ปิด
และแก้ไข แต่ไม่มีทางลบบทเรียน · ปุ่มถังที่หัวหมวดเป็นการลบหมวด ไม่ใช่การลบบทเรียน จึงขอให้
เพิ่มวงจร **เก็บเข้าถัง → กู้คืน → ลบถาวร** โดยต้องไม่ทำให้ประวัติการเรียนหายไปพร้อมเนื้อหา

**R9.1 · การลบบทเรียนต้องเริ่มจาก “เก็บเข้าถัง” เท่านั้น** — `owner` และ `admin` เก็บบทเรียน
เข้าถังได้ครั้งละหนึ่งบทเรียน · เมื่อเข้าถังแล้ว บทเรียนต้องหายจากรายการใช้งานปกติ ใช้เรียนต่อไม่ได้
สร้างลิงก์ใหม่ไม่ได้ และลิงก์เดิมทั้งหมดต้องถูกยกเลิก · ระหว่างที่ยังอยู่ในถังให้เก็บเนื้อหา
และสิ่งที่ผูกกับบทเรียนไว้ เพื่อให้กู้คืนกลับมาได้ครบ · **ผู้เรียนที่กำลังเรียนบทเรียนนั้นค้างอยู่
ณ เวลาที่เก็บเข้าถัง ต้องได้เรียนรอบที่ค้างอยู่จนจบ ไม่ถูกตัดออกจากห้องกลางคัน** — สิ่งที่ถูกปิด
คือการ *เริ่มหรือเข้าร่วมรอบถัดไป* เท่านั้น (เคาะ 2026-08-26 · เจ้าของโปรเจกต์เลือกทางนี้แทน
การเด้งผู้เรียนออกทันที และแทนการห้ามเก็บเข้าถังขณะมีคนเรียนค้าง)

**R9.2 · ถังขยะอยู่เป็นแท็บในหน้าจัดการบทเรียนเดิม** — แสดงเฉพาะบทเรียนในบริษัทเดียวกับ
ผู้ใช้งาน · การเก็บเข้าถัง กู้คืน และลบถาวรทำได้ทีละบทเรียนเท่านั้น **ไม่มี bulk action**

**R9.3 · กู้คืนได้ก่อนถูกลบถาวร** — `owner` และ `admin` กู้คืนบทเรียนจากถังได้ · บทเรียนต้อง
กลับไปยังหมวดเดิมพร้อมเนื้อหา เอกสาร และบทพูดเดิม · **ลิงก์เก่าที่ถูกยกเลิกต้องไม่กลับมาใช้งาน**
หากต้องการแจกบทเรียนอีกครั้งต้องสร้างลิงก์ใหม่

**R9.4 · เก็บในถัง 60 วันแล้วลบถาวรอัตโนมัติ** — เริ่มนับจากเวลาที่เข้าถังครั้งล่าสุด · หากกู้คืน
แล้วนำเข้าถังใหม่ ให้เริ่มนับ 60 วันใหม่ · เมื่อครบกำหนดให้ลบถาวรอัตโนมัติ โดยไม่ต้องขอคำยืนยันซ้ำ
และ **ไม่ส่งอีเมลหรือการแจ้งเตือนภายนอกถังขยะ**

**R9.5 · แสดงเวลาที่เหลือเฉพาะในถังขยะ** — ต้องบอกว่าเหลืออีกกี่วันก่อนลบถาวร โดยใช้ระดับสี:
มากกว่า 14 วันเป็นสถานะปกติ · เหลือ 8–14 วันเป็นสีเหลือง · เหลือ 1–7 วันเป็นสีแดง · วันสุดท้าย
แสดงข้อความ **“จะถูกลบถาวรภายในวันนี้”** · สถานะนี้ไม่ต้องปรากฏในหน้าหรือช่องทางอื่น

**R9.6 · ลบถาวรด้วยมือได้เฉพาะ `owner`** — ทำได้จากถังขยะและครั้งละหนึ่งบทเรียนเท่านั้น ·
ก่อนลบต้องพิมพ์ชื่อบทเรียนให้ตรงเพื่อยืนยัน · การลบอัตโนมัติเมื่อครบ 60 วันไม่ต้องแสดงขั้นยืนยันนี้

**R9.7 · สิ่งที่ต้องหายเมื่อถูกลบถาวร** — ลบตัวบทเรียน เนื้อหา PDF ตัวสไลด์ บทพูด เอกสาร
ที่มี scope เป็นบทเรียนนั้น และ Q&A ที่มี scope เป็นบทเรียนนั้น รวมถึงความรู้ที่ยังใช้ตอบคำถามได้
ของรายการเหล่านั้น · **ห้ามย้ายเอกสารหรือ Q&A ไป scope ระดับบริษัทโดยอัตโนมัติ** · ลบถาวรแล้ว
ไม่มี undo หรือทางกู้คืน

**R9.8 · ประวัติยังอยู่ แต่ต้องไม่กลับมาเป็นงานค้าง** — เก็บ `LearningSession` และคำถามในอดีต
ไว้เพื่อรายงาน โดยแสดงชื่อแทนบทเรียนที่ถูกลบว่า **“บทเรียนที่ถูกลบ”** · คำถามที่ผูกกับบทเรียน
ซึ่งถูกลบถาวรแล้วต้องไม่กลับเข้าสู่คิวตรวจคำถามที่ยังใช้งานอยู่

**R9.9 · แยกข้อมูลตามบริษัทอย่างเคร่งครัด** — ผู้ใช้ต้องเห็นและจัดการได้เฉพาะบทเรียนในบริษัท
ของตนเอง ทั้งรายการใช้งานปกติ ถังขยะ การกู้คืน และการลบถาวร

**ไม่อยู่ในขอบเขต R9:** bulk action · อีเมลหรือ notification เตือนก่อนลบ · การทำให้ลิงก์เก่า
กลับมาใช้ได้ · การย้ายเอกสาร/Q&A ไป scope บริษัท · การกู้คืนหลังลบถาวร

### ผลการสัมภาษณ์รอบ 1 (2026-08-24) — ข้อเสนอเดิมตกไป ปัญหาจริงเป็นเรื่องอื่น

**CR-1.a — ✅ ตอบแล้ว** เจ้าของโปรเจกต์เลือกสองข้อ และ**ไม่ได้เลือก**สองข้อ ซึ่งข้อที่ไม่เลือก
สำคัญเท่าข้อที่เลือก:

| ตัวเลือก | ผล |
|---|---|
| ต้องเลือก scope ทุกครั้ง = friction | **ไม่เลือก** → การเลือก scope เองไม่ใช่ปัญหา |
| มองภาพรวมคลังไม่เห็นเมื่อของเยอะขึ้น | **เลือก** → ปัญหาเรื่องการจัดระเบียบ/การมองเห็น |
| อยากให้ AI ตอบข้ามบทเรียนได้ | **ไม่เลือก** → ไม่ได้ต้องการเปลี่ยน retrieval scope เลย |
| ฟอร์มอัปโหลดใช้ยากในตัวมันเอง | **เลือก** → ปัญหา UX ของฟอร์ม ไม่เกี่ยวกับ scope model |

**CR-1.b — ✅ ตอบแล้ว: "รับไม่ได้เลย"** — คำตอบที่มาจากบทเรียนผิดรับไม่ได้ ไม่มีเงื่อนไข
ตรงกับหัวใจ grounded tutor (`CLAUDE.md` §System Purpose) และ D-07 · ข้อนี้ปิดทุกทางที่จะ
ผ่อนขอบเขต retrieval ให้หลวมลง

**CR-1.c — ⚠️ ตอบด้วยคำของตัวเอง ไม่เลือกตัวเลือกใดเลย** คำพูดตรง:

> "อยากให้แบ่งเป็นส่วนที่เกี่ยวข้องอย่างเดียว แบบ อัพโหลดอันนี้ เป็นกลุ่มความรู้ก้อนนี้ๆๆ
> อะไรประมาณนี้ ไม่อยากให้ก้าวก่ายกัน เพื่อให้ง่ายกับการหาคำตอบ แบ่งแยกไปเลย"

**สิ่งที่สรุปได้แน่นอนจากคำตอบนี้:** เจ้าของโปรเจกต์ต้องการ **แยกให้ชัดขึ้น** เพื่อให้หาคำตอบ
ง่ายขึ้น — ซึ่งเป็น**ทิศทางตรงข้ามกับข้อเสนอเดิมของ CR-1** (ยุบรวมกองเดียว) และเหตุผลที่ยกมา
("เพื่อให้ง่ายกับการหาคำตอบ") คือสิ่งเดียวกับที่ข้อเสนอเดิมยอมแลกทิ้ง

**❌ สรุป: ข้อเสนอเดิมของ CR-1 (ยุบ scope เหลือกองเดียว) ถือว่าตกไป** — CR-1.a ไม่เลือกทั้ง
friction และ cross-lesson · CR-1.b ปฏิเสธการตอบข้ามบทเรียนเด็ดขาด · CR-1.c ขอให้แยกชัดขึ้น
ไม่ใช่รวมเข้าด้วยกัน → **`docs/HANDOFF_MASTER.md` ข้อ 5 และ R3 ไม่ถูกรื้อ ยังมีผลบังคับเต็มที่**
(บันทึกไว้ที่ §"ที่ตัดออกจากเฟสนี้โดยตั้งใจ" ท้ายเอกสารด้วย) · **CR-1.d และ CR-1.e จึงไม่ต้องตอบ**
เพราะทั้งสองข้อมีเงื่อนไขว่า "ถ้ารื้อจริง"

**ข้อเท็จจริงเพิ่มที่พบตอนตรวจ `design.md` รอบนี้ (ไม่มีใน CR-1 เดิม):** KS-1 ผูก
`KnowledgeQnA` ไว้กับ scope model เดียวกับ `DocumentResource` โดยเจตนา เพื่อ resolve namespace
ด้วยฟังก์ชันเดียว ดังนั้นการยุบ scope จะลาก **R5.4** (CS เลือก scope ตอนบันทึกคำตอบ) ไปด้วย
ทั้งกอง ซึ่ง R5.4 มีเหตุผลทางธุรกิจที่เคาะแยกไว้เองแล้ว — เหตุผลเพิ่มอีกข้อที่ข้อเสนอเดิมไม่ผ่าน
