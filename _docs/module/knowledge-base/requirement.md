# Requirement — Knowledge Base & Teaching Content Intake

**โมดูล:** `knowledge-base` · **สถานะ:** เก็บ requirement (ยังไม่ครบ ยังไม่ส่งต่อ `system-analyst`)
**ที่มา:** เจ้าของโปรเจกต์ยกประเด็นเมื่อ 2026-08-18 ว่าภาพรวมระบบ "ยังไม่ครบวงจร" —
ครึ่งซ้ายของวงจร (เตรียมความรู้ → แจกลิงก์ → เรียน → จับคำถาม) ทำงานได้แล้ว แต่ครึ่งขวา
(รีวิว → แก้ความรู้ → รู้ว่าดีขึ้น) ตัน

> เอกสารนี้เก็บ **ความต้องการทางธุรกิจ** ไม่ใช่วิธีทำ · `docs/KNOWLEDGE_ROADMAP.md` ที่มีอยู่แล้ว
> เป็น roadmap เชิงเทคนิคของ retrieval/eval — คนละชั้นกับเอกสารนี้ ไม่ทับกัน อ่านคู่กันได้

(บทเรียนต้องมีหมวดเสมอตามมติ R1.1) ไม่ใช่งานแยกที่ทำเมื่อไหร่ก็ได้ — `system-analyst`/`project-manager`
ควรนับ "สร้างหน้าสร้างบทเรียน + เลือกหมวด" เป็นงานเดียวกัน ไม่ใช่สองงานที่ทำคนละรอบ

## Requirement ที่เจ้าของโปรเจกต์เคาะแล้ว

### R1 · Taxonomy 3 ชั้น (✅ เคาะ 2026-08-19)

`category > subcategory > ชื่อเนื้อหา` ใช้กับ **ทั้งบทเรียนและเอกสาร** ทำหน้าที่สองอย่างพร้อมกัน:
จัดเก็บให้เป็นระเบียบตั้งแต่ตอนนำเข้า และเป็นเมนูค้นหา (คล้าย sidebar/megamenu) ตอนต้องหา
บทเรียน/สื่อการสอน/เทรนนิ่ง

**R1.1 · หนึ่งบทเรียนอยู่ได้หมวดเดียว และต้องมีหมวดเสมอ** (✅ เคาะ 2026-08-19) —
เหมือนไฟล์ในโฟลเดอร์ ไม่ใช่ป้ายกำกับ · ทำให้เมนูชัดและความรู้ระดับหมวด (R3) ไม่กำกวม
**ผลที่ต้องรับ:** บทเรียนที่คร่อมสองหมวดจริง ๆ ต้องเลือกข้างเดียว และ**ข้อมูลเดิมที่มีอยู่แล้ว
ต้องถูกจัดหมวดให้ครบก่อนเปิดใช้ฟีเจอร์นี้**

**R1.2 · ลบหมวดที่ยังมีบทเรียนหรือเอกสารอยู่ไม่ได้** (อนุมานจาก R1.1 — ยังไม่ได้ยืนยันตรง ๆ) —
เพราะบทเรียนต้องมีหมวดเสมอ การลบหมวดจึงต้องบล็อกไว้จนกว่าจะย้ายของออกหมด

### R2 · แต่ละบริษัทจัดหมวดของตัวเอง (✅ เคาะ 2026-08-19)

admin/cs ของบริษัทสร้างและแก้หมวดของตัวเองได้ **ไม่ใช่** School Bright กำหนดชุดกลาง —
เข้ากันกับโครงข้อมูลเดิมที่ทุกอย่างแยกตามบริษัทด้วย `CompanyId` + query filter

**ผลข้างเคียงที่ยอมรับแล้ว:** ทุกบริษัทต้องตั้งหมวดเองตั้งแต่เริ่มใช้งาน · หมวดไม่เหมือนกัน
ข้ามบริษัท ทำให้รายงานเทียบข้ามบริษัท ("หมวดการเงินมีปัญหาบ่อยสุดทุกบริษัท") ทำไม่ได้ในเฟสนี้

### R3 · คลังความรู้ 3 ระดับ (✅ เคาะ 2026-08-19)

บทเรียน / **หมวด** / ทั้งบริษัท — เอกสารที่วางระดับหมวดต้องตอบได้ทุกบทเรียนในหมวดนั้น
แต่ไม่โผล่ไปหมวดอื่น · ปัจจุบันมีแค่ระดับบนสุดกับล่างสุด

**ต้องรู้:** ทุกคำถามยิงทุก namespace พร้อมกัน การเพิ่มระดับที่สามคือ query ที่เพิ่มขึ้นต่อคำถาม

**R3.1 · ย้ายบทเรียนข้ามหมวด = ความรู้ที่ใช้ตอบเปลี่ยนตามหมวดใหม่ทันที และต้องเตือนก่อนย้าย**
(✅ เคาะ 2026-08-19) — บทเรียนจะเลิกเข้าถึงเอกสารระดับหมวดเดิมและเริ่มเข้าถึงของหมวดใหม่
ทันทีที่ย้าย ซึ่งแปลว่า **คำตอบของ AI สำหรับบทเรียนนั้นเปลี่ยนทันทีโดยไม่มีใครสั่งโดยตรง** ·
ตอนกดย้ายต้องบอกให้ชัดว่าจะเลิกใช้เอกสารกี่ชิ้นและจะเริ่มใช้ของหมวดใหม่แทน แล้วให้ยืนยัน

### R4 · ขาเข้าสื่อการสอน — บทพูดที่แก้ได้ (✅ เคาะ 2026-08-19)

**แยกทางเดินตาม `ContentSourceType` ชัดเจน:**

| แหล่ง | บทพูดมาจาก | แก้ที่ไหน |
|---|---|---|
| `google_slides` | Speaker Notes | **แก้ที่ Google Slides ตามปกติ ไม่มีช่องแก้ในระบบ** — ทีม School Bright สร้างเด็คเองทุกเด็คและแก้ได้ จึงไม่ต้องมีบทพูดสองที่ให้สับสน (สอดคล้องกฎสถาปัตยกรรมข้อ 8) |
| `pdf` | ข้อความบนหน้า | **มีช่องบทพูดต่อหน้าในระบบ** prefill ด้วยข้อความที่ระบบดึงได้ CS แก้ทับได้ |

กติกาของช่องบทพูด PDF:
1. **เก็บเฉพาะหน้าที่ CS แก้จริง** — ห้ามเซฟข้อความ prefill ของหน้าที่ไม่ได้แตะลงฐานข้อมูล
   ไม่งั้นเป็นการแช่แข็งสำเนาที่พังไว้ถาวร และการปรับตัวแปลงให้ดีขึ้นวันหลังจะไม่มีผลกับหน้าเหล่านั้น
2. **มีค่าที่แก้ไว้ = ใช้ค่านั้นเสมอ** ไม่มีค่า = ใช้ข้อความที่ดึงจากไฟล์
3. **อัปโหลด PDF ใหม่ = ล้างบทพูดที่แก้ไว้ทั้งหมด** ต้องเตือนจำนวนหน้าที่จะถูกลบและให้ยืนยันก่อน
   (เหตุผล: id ต่อหน้าของ PDF คือ `pdf-page-N` ผูกกับเลขหน้าล้วน แทรกหน้าใหม่ 1 หน้า
   บทพูดทุกหน้าถัดไปจะเลื่อนผิดโดยไม่มี error — ล้างทิ้งชัดเจนกว่าเดาว่าหน้าไหนคือหน้าไหน)
4. **PDF สแกนที่ดึงข้อความไม่ได้เลย → เตือนชัดว่าเป็นไฟล์สแกน ต้องพิมพ์บทพูดเองทุกหน้า**
   ไม่ทำ OCR ในเฟสนี้ · ข้อเท็จจริงวันนี้ (ตรวจโค้ดแล้ว 2026-08-19): ฝั่ง **คลังความรู้** จับได้
   อยู่แล้ว — ได้ 0 chunk จะตั้งสถานะเป็น `failed` ไม่ได้ขึ้นว่าสำเร็จ · แต่ฝั่ง **บทพูด** ไม่มีใคร
   ตรวจเลย ไฟล์สแกนจะได้บทพูดว่างทุกหน้าแล้วห้องเรียนก็เงียบ โดยไม่มีอะไรเตือน CS ก่อนถึงหน้างาน
5. **บทพูดที่แก้แล้วต้องมีผลกับคำตอบของ AI ด้วย** — สิ่งที่ AI พูดกับสิ่งที่ AI ใช้ตอบต้องเป็น
   เรื่องเดียวกัน ดังนั้นแก้บทพูดแล้วต้อง re-index หน้านั้น (chunk id ผูกกับหน้าอยู่แล้ว
   จึง upsert เฉพาะหน้าที่แก้ได้ ไม่ต้อง re-embed ทั้งเด็ค)

**ข้อเท็จจริงที่ต้องแก้ไปพร้อมกัน:** วันนี้บทเรียน PDF ใช้ข้อความจากไฟล์เดียวกันสองเส้นทาง
คนละตัวแปลง — บทพูดมาจาก `PdfSlidesRenderer` (เก็บหน้าว่างไว้) ส่วนคำตอบมาจาก
`PdfTextExtractor` ผ่านเอกสารแนบ (ตัดหน้าว่าง) และบทเรียน PDF ไม่เคยถูก index เข้า namespace
ของบทเรียนตัวเองเลย (`ILessonConfigService` index เฉพาะบทที่มี `presentationId`)

### R5 · คลังความรู้เป็น Q&A ที่โตจากคำถามจริง (✅ เคาะ 2026-08-19)

**แนวคิดหลักมาจากเจ้าของโปรเจกต์: คลังความรู้คือคู่ถาม-ตอบ ไม่ใช่เอกสารอย่างเดียว**
"ถามประมาณไหน ตอบประมาณนั้น — พอผู้ใช้ถามมาประมาณไหน ก็เอาคำตอบประมาณนั้นไปตอบ"

สิ่งนี้เปลี่ยนวิธีปิดวงจร: เดิม CS กด "ตอบผิด" แล้วต้องไปเขียนเอกสารใหม่ → อัปโหลด → รอ index
ซึ่งขั้นตอนเยอะจนไม่มีใครทำจริง · ใหม่คือ **CS เขียนคำตอบที่ถูกลงไปตรงจุดที่เจอปัญหาเลย**

**R5.1 · คิวงาน = คำถามที่ยังไม่มีคำตอบที่ถูก — มาจากสองแหล่ง ต้องแยกให้เห็นว่ามาจากไหน**

| แหล่ง | เกิดเมื่อ | ต้นทุน |
|---|---|---|
| `answerStatus = not_found` | AI รู้ตัวเองว่าไม่มีข้อมูล — เข้าคิว**อัตโนมัติ** | ฟรี ไม่ต้องมีคนอ่าน · น่าจะเป็นปริมาณหลัก |
| CS กด "ตอบผิด" | คนอ่านย้อนหลังแล้วพบว่า AI มั่นใจแต่ตอบผิด | ใช้เวลาคน · แต่จับสิ่งที่แหล่งแรกจับไม่ได้เลย |

วันนี้ทั้งสองแหล่งกระจายอยู่ในหน้าสรุปของแต่ละการเรียน — ลิงก์เดียวมีผู้เรียน 40 คน ต้องเปิดดู
40 หน้าถึงจะรู้ว่ามีคำถามอะไรที่ตอบไม่ได้ · **ต้องมีหน้าเดียวที่รวมข้ามการเรียนและข้ามบทเรียน**

**R5.2 · การปิดงานเกิดเอง ไม่ต้องมีปุ่ม "แก้แล้ว"** — คำถามที่มีคำตอบที่ถูกแล้วคือคำถามที่ออกจากคิว
ไม่มีสถานะ workflow แยก ไม่มีการส่งงานต่อไปหาใคร (ผลพลอยได้จากการแก้ตรงจุด)

**R5.3 · AI ใช้ Q&A เป็นหลักฐาน แล้วเรียบเรียงใหม่ ห้ามคัดลอกมาตอบตรง ๆ**
เหตุผล: คำถามที่ใกล้กันมากในเชิงภาษาอาจต่างกันคนละเรื่องในสาระ
("ลบข้อมูลนักเรียนยังไง" กับ "ลบข้อมูลนักเรียนที่จบไปแล้วยังไง") · การเรียบเรียงใหม่ทำให้ AI
ยังปฏิเสธได้เมื่อ Q&A ที่หยิบมาไม่ตรงคำถามจริง ซึ่งการคัดลอกมาวางทำไม่ได้

**R5.4 · CS เลือก scope ตอนบันทึกคำตอบ** — บทเรียนนี้ / ทั้งหมวด / ทั้งบริษัท (ตรงกับ R3)
เพราะคำถามจำนวนมากเป็นเรื่องทั่วไปที่ไม่ผูกกับบทเรียนที่บังเอิญถูกถามตอนนั้น

**R5.5 · เมื่อ Q&A ขัดกับสไลด์/เอกสาร → เอกสารชนะ และต้องยกธงให้คนเห็น**
AI ตอบตามเอกสารไปก่อน **แต่ต้องขึ้นรายการให้ CS เห็นว่า Q&A นี้ขัดกับเอกสาร** เพื่อไปแก้เอกสาร
ที่เป็นต้นเหตุจริง · เหตุผลที่ต้องมีธง: ถ้าเอกสารชนะเงียบ ๆ เคสที่ AI ตีความเอกสารกำกวมผิด
จะแก้ไม่ได้เลยด้วย Q&A และจะตอบผิดซ้ำเรื่อย ๆ โดยไม่มีใครรู้ว่าเอกสารเป็นต้นเหตุ

**ข้อจำกัดที่ต้องยอมรับ:** ลำดับความสำคัญนี้บังคับได้แค่ระดับ prompt (ส่งทั้งเอกสารและ Q&A
เข้าไปพร้อมคำสั่งว่าให้ยึดเอกสารเมื่อขัดกัน) **ไม่ใช่กลไกที่บังคับได้จริงเหมือนโค้ด** และตัว AI
เป็นคนตัดสินเองว่าอะไรคือ "ขัดกัน"

**R5.7 · `cs` เขียนคำตอบแล้วใช้ได้ทันที ไม่ต้องรออนุมัติ** (✅ เคาะ 2026-08-19) —

(รู้ว่าใครเขียน เมื่อไหร่ และแก้/ลบได้)

### R6 · ความน่าเชื่อถือของขาเข้าเอกสาร (✅ เคาะ 2026-08-19)

> **บริบท — อัปโหลด 1 ไฟล์มี 5 ขั้น:** (1) เก็บไฟล์ + บันทึก metadata → (2) เข้าคิวรอทำเบื้องหลัง
> → (3) แปลงไฟล์เป็นข้อความทีละหน้า → (4) แปลงข้อความเป็น embedding (เสียเงินจริง) →
> (5) เก็บลง Pinecone รอให้ AI หยิบไปตอบ · R6 แก้ขั้น 2, 3 และ 5

**R6.1 · ลบเอกสาร = soft delete ในฐานข้อมูล + ลบ vector ออกจาก Pinecone จริง**

แยกสองที่ให้ชัด เพราะพฤติกรรมต่างกันโดยสิ้นเชิง:

| | ฐานข้อมูล | Pinecone |
|---|---|---|
| วิธีลบ | **soft delete** (`IsDelete`/`DeletedAt` มีอยู่ในทุก entity แล้ว) กู้คืนได้ | **ลบจริง** |
| ทำไม | เก็บประวัติ กู้คืนได้ ตรงกับแบบแผนของระบบส่วนใหญ่ | ไม่มี query filter แบบฐานข้อมูล · ถ้า vector ยังอยู่ AI ก็ยังหยิบมาตอบ soft delete จึงไม่มีความหมายที่นี่ |

กู้คืนเอกสาร = แปลงและ index ใหม่จากไฟล์ที่ยังอยู่ (ขั้น 3–5 ซ้ำ เสียค่า embedding อีกรอบ
ยอมรับได้) · chunk id เป็น `{documentId}-{chunkId}` อยู่แล้วจึงลบด้วย id prefix ได้ตรง ๆ
**แต่ `IKnowledgeIndexProvider` วันนี้มีแค่ `DeleteNamespaceAsync` (ลบทั้ง namespace)
ต้องเพิ่มความสามารถลบทีละชุด**

**R6.2 · คิวงานเก็บลงฐานข้อมูล และทำงานที่ค้างต่อเองตอนสตาร์ต**

วันนี้คิวอยู่ในหน่วยความจำล้วน (`BackgroundTaskQueue`) — restart เมื่อไหร่งานที่รออยู่หายหมด
เอกสารค้างสถานะ `pending` ตลอดกาลโดยไม่มีใครรู้ · ต้องเก็บงานลง DB และเมื่อระบบสตาร์ตใหม่
ให้ไล่เก็บงานที่ค้างมาทำต่อเอง **ไม่ต้องรอ CS มากดลองใหม่** · ล้มแล้วลองซ้ำได้เอง

**R6.3 · CS เปิดดูข้อความที่แปลงได้ (ขั้น 3) ได้ตลอด ทุกไฟล์ ไม่ใช่เฉพาะตอนล้มเหลว**

เหตุผลที่ต้องดูได้แม้ไฟล์ที่ขึ้นว่าสำเร็จ: ระบบตรวจได้แค่ว่า "ว่างเปล่าหรือไม่" ตรวจไม่ได้ว่า
"เสียหายหรือไม่" — ไฟล์ที่ตัวอักษรไทยเพี้ยน (วรรณยุกต์กลายเป็นอักขระเสีย ตามที่พบจริงในการ
ทดสอบ 2026-08-19) จะแปลงได้ข้อความจำนวนมาก ขึ้นสถานะ `indexed` ตามปกติ ทั้งที่คลังความรู้
เพิ่งรับข้อความเสียเข้าไป · **สายตาคนคือทางเดียวที่จับเคสนี้ได้**

**R6.4 · สถานะล้มเหลวต้องบอกสาเหตุ** — วันนี้ `failed` ครอบทั้งแปลงไฟล์ไม่ได้ / ได้ข้อความเปล่า /
embedding ล่ม ซึ่งวิธีแก้คนละเรื่องกัน (เปลี่ยนไฟล์ / พิมพ์เอง / ลองใหม่) ต้องแยกให้ CS รู้ว่า
ต้องทำอะไรต่อ · ห้ามแสดงรายละเอียดภายในของ provider หรือ error ดิบให้ผู้ใช้เห็น

### CR-1 · รวม knowledge scope "เฉพาะบทเรียน" กับ "ทั้งบริษัท" ให้เหลือกองเดียว

**ต้นเรื่อง**: เจ้าของโปรเจกต์ใช้งาน UI อัปโหลดเอกสารต่อบทเรียนจริง
(`frontend/src/components/admin/DocumentUploadList.tsx`) แล้วรู้สึกว่า **แข็งและจุกจิกเกินไป** —
CS ต้องตัดสินใจเรื่อง scope ทุกครั้งที่อัปโหลด

**ข้อเสนอตามที่เจ้าของโปรเจกต์พูดเอง**: เลิกให้ CS เลือก scope ตอนอัปโหลด → โยนทุกอย่างเข้ากอง
**ระดับบริษัทกองเดียว** แล้วปล่อยให้ relevance scoring ตอน retrieve (RAG) คัดเองว่าอะไรเกี่ยวกับ
บทเรียนที่กำลังถูกถาม และทิ้งของที่คะแนนต่ำเหมือนที่ทำอยู่แล้วในเคส `not_found`

**สิ่งที่ข้อเสนอนี้ *ไม่* ได้เสนอ**: **ไม่ได้เสนอให้ข้ามบริษัท** — กำแพง multi-tenant
ยังแข็งเหมือนเดิมทุกประการ เรื่องนี้อยู่ภายในบริษัทเดียวล้วนๆ

**⚠️ ข้อนี้ขัดกับมติที่ประกาศห้ามเปลี่ยนเงียบๆ**: `docs/HANDOFF_MASTER.md` §"Product decisions
ที่เคาะแล้ว — ห้ามทีมเปลี่ยนเงียบ ๆ" ข้อ 5 เขียนไว้ว่า *"Knowledge มี 2 scope: เฉพาะบทเรียน
และ global ของบริษัทนั้น; ห้ามข้ามบริษัท"* · และในโมดูลนี้เองมติที่เคาะแล้วคือ **R3 คลังความรู้
3 ระดับ (บทเรียน/หมวด/ทั้งบริษัท)** ซึ่งเดินหน้าไปเป็น implementation จริงแล้ว (Phase 1–7
verified) → **การรับข้อเสนอนี้ = การรื้อมติ ต้องผ่านการสัมภาษณ์เต็มรูปแบบ ไม่ใช่ amend สั้นๆ**

**ความเสี่ยงเชิงความแม่นยำ/สถาปัตยกรรมที่ยกขึ้นในการคุยรอบนี้ และเจ้าของโปรเจกต์ให้บันทึกไว้
แทนที่จะเคาะทันที** (นี่คือประเด็นที่ยังไม่มีคำตอบ ไม่ใช่การปฏิเสธข้อเสนอ):

1. **สองบทเรียนในบริษัทเดียวกันใช้คำศัพท์ร่วมกันได้** — ตัวอย่างของเจ้าของโปรเจกต์เอง:
   "การลงเวลา" โผล่ได้ทั้งในบทเรียนเช็คชื่อและบทเรียนเงินเดือน · การค้นด้วยความคล้ายเชิงความหมาย
   ล้วนโดยไม่มีขอบเขตบทเรียนที่ชัดเจน **เสี่ยงหยิบเนื้อหาของบทเรียนผิดมาตอบ**
2. ข้อ 1 **สวนทางกับหัวใจของระบบโดยตรง** — "grounded tutor: ตอบ `not_found` อย่างมั่นใจ
   ดีกว่าเดา" (root `CLAUDE.md` §System Purpose) และ D-07 ใน `docs/HANDOFF_MASTER.md`
   ที่ตั้งความแม่นของ not-found เป็นเป้าคุณภาพ · ตอบผิดบทเรียน **แย่กว่า** ตอบว่าไม่รู้
3. **ทิ้งสถาปัตยกรรม namespace ที่มีอยู่** — วันนี้ Pinecone ใช้ `namespace = lessonSlug`
   หรือ `kb-global` (root `CLAUDE.md` §Existing Integrations) และ Phase 2 ของโมดูลนี้เพิ่งทำ
   3-namespace query (lesson + category + global) เสร็จไป · การยุบเหลือกองเดียวทำให้ candidate set
   ต่อ query ใหญ่ขึ้นและถูกกรองน้อยลง = **อาจถดถอยทั้งคุณภาพ retrieval, latency และค่าใช้จ่าย
   ไม่ใช่แค่เรื่อง UI** · ยังไม่มีตัวเลขวัดจริง (R-2 latency ยังไม่เคยวัด เพราะยังไม่ deploy)

**ทางสายกลางที่ถูกเสนอในรอบนี้ — เจ้าของโปรเจกต์ยัง *ไม่รับและไม่ปฏิเสธ*** (บันทึกไว้เป็น

- **override บทพูดฝั่ง Google Slides** — ทีมสร้างเด็คเองและแก้ได้ จึงไม่จำเป็น
  ถ้าวันหนึ่งมีเด็คของลูกค้าที่แก้ไม่ได้ ต้องกลับมา amend เอกสารนี้ก่อน
- **หมวดกลางที่ School Bright กำหนด** และรายงานเทียบข้ามบริษัท (ผลของ R2)
- **PPTX เป็นสื่อสอนหลัก** — วันนี้ parse ได้แต่เข้าคลังความรู้เท่านั้น ยังไม่มีคนขอ
- **auto-detect ว่าเด็คต้นทางถูกแก้** — วันนี้ต้องกด save ที่ระบบเพื่อ sync/re-index เอง
- **ยุบ knowledge scope เหลือกองเดียวระดับบริษัท (ข้อเสนอเดิมของ CR-1)** — ปิด 2026-08-24
  จากการสัมภาษณ์เจ้าของโปรเจกต์เอง (ไม่ใช่คำตัดสิน feasibility ของ `system-analyst`) ·
  เหตุผล: เจ้าของโปรเจกต์ยืนยันว่าคำตอบที่มาจากบทเรียนผิด "รับไม่ได้เลย" (CR-1.b) ·
  ไม่ได้เลือก "ต้องเลือก scope ทุกครั้งน่ารำคาญ" และไม่ได้เลือก "อยากให้ AI ตอบข้ามบทเรียน"
  เป็นปัญหา (CR-1.a) · และสิ่งที่ขอจริงคือ "แบ่งแยกไปเลย ไม่อยากให้ก้าวก่ายกัน" ซึ่งเป็นทิศทาง
  ตรงข้าม (CR-1.c) → **R3 และ `docs/HANDOFF_MASTER.md` ข้อ 5 ไม่ถูกรื้อ** · ถ้ามีคนเสนอเรื่องนี้
  อีกให้กลับมาอ่านข้อนี้ก่อน ไม่ต้องวิเคราะห์ใหม่ตั้งแต่ศูนย์ ·
  **ยืนยันซ้ำในรอบ 2 (CR-1.g)**: เจ้าของโปรเจกต์ระบุว่าพฤติกรรมการค้นคำตอบวันนี้ถูกต้องแล้ว
  "เป็นแค่เรื่องมองเห็น/จัดเก็บ ไม่ใช่เรื่องคำตอบ" → ปิดทั้งทางที่จะทำให้ scope **หลวมลง**
  (ข้อเสนอเดิม) และทางที่จะทำให้ **แคบลง** (เช่น ตัดระดับ "ทั้งบริษัท" ออก) ·
  งานที่ค้นพบแทนถูกยกขึ้นเป็น **R7/R8** ซึ่งเป็นงาน UI/การมองเห็นล้วน
- **การรัดขอบเขต retrieval ให้แคบลงกว่า R3** (เช่น เลิกใช้ระดับ "ทั้งบริษัท" หรือบังคับให้
  ทุกเอกสารผูกบทเรียน) — ปิด 2026-08-24 จากคำตอบ CR-1.g · เป็นทางที่ `business-analyst`
  เปิดถามเองเพราะคำว่า "ไม่อยากให้ก้าวก่ายกัน" ฟังเหมือนต้องการสิ่งนี้ แต่เจ้าของโปรเจกต์
  ปฏิเสธชัดเจนว่าไม่ได้หมายถึงเรื่องคำตอบ
