# การรับลูกค้าใหม่และตั้งค่าระดับบริษัท (company-admin) — Requirements

> โมดูลนี้แยกจาก `knowledge-base` และ `learning-session` โดยตั้งใจ (ยืนยัน 2026-08-21):
> สองโมดูลนั้นตอบว่า "ความรู้ถูกดูแลยังไง" และ "การเรียนเกิดขึ้นยังไง" — โมดูลนี้ตอบว่า
> "School Bright รับลูกค้ารายใหม่เข้าระบบยังไง และปรับระบบให้เข้ากับลูกค้าแต่ละรายยังไง"
> ผู้ใช้หลักคนละกลุ่ม (owner ของ School Bright / admin ของบริษัทลูกค้า ไม่ใช่ CS ที่ดูแลเนื้อหา)
> และตัดทั้งก้อนออกได้โดยไม่กระทบสองโมดูลเดิม → ตรงกฎ `conventions.md` §1
> ("จะได้สัมภาษณ์ business แยกของตัวเองไหม")

## Overview

วันนี้ระบบรับลูกค้าใหม่ทาง UI ไม่ได้เลย ต้องมีคน insert แถวลง database ตรงๆ และไม่มีทาง
ปรับค่าอะไรให้ต่างกันต่อบริษัทได้เลยเพราะทุกค่าเป็น environment variable ระดับ deployment
เดียวใช้ร่วมกันทั้งระบบ โมดูลนี้ปิดช่องว่างสองข้อนั้น: หน้าจอสำหรับ owner สร้างบริษัทลูกค้าใหม่
ให้พร้อมใช้งานได้จริงตั้งแต่คลิกเดียว และหน้าตั้งค่าระดับบริษัทสำหรับ 3 ค่าที่ลูกค้ารู้สึกถึง
ความแตกต่างได้จริง กระทบ business model โดยตรง ไม่ใช่ nice-to-have — ทุกวันนี้ทีมขายรับ
ลูกค้าใหม่ไม่ได้ถ้าไม่มีคนเข้าถึง database

## ปัญหาที่ต้องแก้ (ยืนยันจากโค้ดจริง 2026-08-21 ไม่ใช่การอนุมาน)

| # | ปัญหา | หลักฐานในโค้ด |
|---|---|---|
| P1 | สร้างบริษัทใหม่ไม่มี UI เลย | `POST /api/companies` มีจริงที่ `CompanyController.cs:26` และ `createCompany()` มีจริงที่ `frontend/src/lib/api-client.ts:559` แต่ grep ทั้ง `frontend/src` แล้ว **ไม่มีไฟล์ใดเรียกฟังก์ชันนี้เลย** มีแค่บรรทัดที่ประกาศตัวมันเอง |
| P2 | ไม่มีการตั้งค่าระดับบริษัท | ไม่มี entity `CompanySettings`/`CompanyConfig` ที่ไหนในทั้ง repo · `DEFAULT_SESSION_EXPIRY_HOURS` อ่านที่ `ServerDefaults.cs:46` จุดเดียวจาก env · `EDGE_TTS_VOICE`/`EDGE_TTS_RATE` อ่านที่ `ServerDefaults.cs:271-273` เช่นกัน · `Company` entity มีแค่ `Id`/`Name`/`IsActive` + audit fields |
| P3 | บริษัทที่สร้างใหม่จะ **ไม่มี default category chain** | `knowledge-base` มี invariant ว่าทุกบริษัทต้องมีแถว `IsSystemDefault` สองชั้นพอดี (parent Level 1 + leaf Level 2) แต่คนที่สร้างให้คือ **migration** `20260819082956_AddKnowledgeTaxonomyAndScope.cs:46-48` เท่านั้น — ไม่มีโค้ด runtime ที่ไหนสร้างให้ บริษัทที่เกิดหลัง migration จะ `GetSystemDefault()` (`IKnowledgeCategoryRepository.cs:28`) คืน null และพังตอนสร้างบทเรียน |

## Target Users & Roles

ระบบมี role อยู่แล้ว 3 ระดับ (`AdminUser.Role`) — โมดูลนี้ไม่เพิ่ม role ใหม่:

| Role | ขอบเขตวันนี้ | สิทธิ์ใหม่ในโมดูลนี้ |
|---|---|---|
| `owner` | School Bright เอง · `CompanyId = null` · เห็นทุกบริษัท | **สร้างบริษัทใหม่ได้ (คนเดียวเท่านั้น)** · แก้ตั้งค่าของทุกบริษัท |
| `admin` | ผูกกับบริษัทเดียว | **แก้ตั้งค่าของบริษัทตัวเองได้** · สร้างบริษัทไม่ได้ |
| `cs` | ผูกกับบริษัทเดียว ดูแลเนื้อหา/คิว Q&A | ไม่มีสิทธิ์ใหม่ — อ่านอย่างเดียวหรือไม่เห็นหน้านี้เลย (ดู Open Question OQ-5) |

## Core Features

### F1 · สร้างบริษัทใหม่แบบฟอร์มเดียวจบ (✅ เคาะ 2026-08-21)

**F1.1** เฉพาะ `owner` เท่านั้นที่เข้าถึงหน้านี้และเรียก endpoint สร้างบริษัทได้ — `admin`/`cs`
ต้องถูกปฏิเสธที่ server ไม่ใช่แค่ซ่อนปุ่มใน UI

**F1.2 — ฟอร์มเดียวจบ**: owner กรอกข้อมูลบริษัท + **อีเมลของ admin คนแรกของบริษัทนั้น**
ในฟอร์มเดียว แล้วระบบสร้างให้พร้อมกันในการกดครั้งเดียว:
1. แถว `Company`
2. แถว `AdminUser` role = `admin` ผูกกับ `CompanyId` ที่เพิ่งสร้าง
3. `KnowledgeCategory` default chain (ดู F1.3)

เหตุผลที่ต้องเป็นฟอร์มเดียว: สร้าง `Company` เปล่าๆ แล้วยังไม่มีใครล็อกอินเข้าบริษัทนั้นได้เลย
(ปัญหาไก่กับไข่แบบเดียวกับที่ `FirstOwnerSeed` แก้ไว้สำหรับ owner คนแรกของทั้งระบบ) —
"สร้างบริษัทแล้ว" ต้องแปลว่า "ลูกค้ารายนั้นเข้าใช้งานได้จริง" ไม่ใช่แค่มีแถวใน database

**F1.3 — ของตั้งต้นที่ต้องสร้างให้อัตโนมัติ**: `KnowledgeCategory` default chain รูปแบบเดียวกับ
ที่ migration backfill ทำไว้ — flagged parent Level 1 + leaf Level 2 ที่เชื่อมกัน ติดธง
`IsSystemDefault` **ทั้งสองแถว** และต้องมี leaf ที่ `IsSystemDefault && Level == 2` เพียงแถวเดียว
ต่อบริษัท (สองแถวเมื่อไหร่ `GetSystemDefault()` จะ throw ทันทีตามที่ repository เขียนไว้)

**F1.4** ถ้าการสร้างขั้นใดขั้นหนึ่งล้มเหลว ต้องไม่เหลือบริษัทครึ่งๆ กลางๆ ไว้ในระบบ —
ทั้งสามอย่างสำเร็จพร้อมกันหรือไม่เกิดอะไรเลย

**F1.5** ต้องกันอีเมลซ้ำตั้งแต่ในฟอร์ม — `AdminUser.Email` unique ข้ามทั้งระบบ ไม่ใช่แค่ต่อบริษัท
(ตาม comment ใน `AdminUser.cs:33-35`) การกรอกอีเมลที่มีคนใช้แล้วต้องได้ข้อความบอกชัด
ไม่ใช่ error 500

**F1.6** หน้ารายการบริษัททั้งหมดสำหรับ owner (ดูว่ามีลูกค้ากี่ราย ใครยัง active) และปุ่มปิดใช้งาน
บริษัท (`IsActive = false` — เป็นวิธี offboard ลูกค้าโดยไม่ทำลายประวัติ ตาม comment ใน
`Company.cs:28-29`) — `PUT /api/companies/{id}` มีอยู่แล้ว รอ UI

### F2 · ตั้งค่าระดับบริษัท (✅ เคาะ 2026-08-21)

**F2.1 — ค่าที่ปรับได้ มี 3 ข้อเท่านั้น** (ที่เหลือตัดออกโดยตั้งใจ ดู `## Declined / Not Pursuing`):

| ค่า | วันนี้ | หมายเหตุ |
|---|---|---|
| **ลิงก์หมดอายุกี่ชั่วโมง** | `DEFAULT_SESSION_EXPIRY_HOURS` = 24 (env) | เป็นค่า default ต่อบริษัท ไม่ใช่ค่าตายตัวต่อลิงก์ |
| **เสียง TTS + ความเร็วพูด** | `EDGE_TTS_VOICE`/`EDGE_TTS_RATE` (env) | วันนี้ไม่มี UI ปรับเสียงเลยแม้แต่นิดเดียว · เชื่อมกับแผนเปลี่ยนไป ElevenLabs ที่คุยไว้ก่อนหน้า (ดู OQ-3) |
| **ชื่อ/โลโก้/สีแบรนด์ที่ผู้เรียนเห็นตอนเข้าห้องเรียน** | ไม่มีเลย | เป็นสิ่งเดียวในสามข้อที่ **ผู้เรียนเห็น** ไม่ใช่ค่าที่ทำงานอยู่เบื้องหลัง |

**F2.2 — รูปแบบ override: ไม่ตั้ง = ใช้ค่ากลาง** (null = inherit จาก env) ไม่ใช่คัดลอกค่ากลาง
มาเก็บตอนสร้างบริษัท — เพื่อให้แก้ค่ากลางที่ deployment แล้วมีผลกับทุกบริษัทที่ไม่เคยตั้งค่าเอง
และหน้าจอต้องแสดงชัดว่าค่าที่เห็นตอนนี้ "สืบทอดมา" หรือ "ตั้งเอง" พร้อมทางกลับไปใช้ค่ากลาง

**F2.3 — สิทธิ์แก้ไข: `owner` + `admin` ของบริษัทนั้น** · `admin` ของบริษัท A ต้องแก้ค่าของ
บริษัท B ไม่ได้ ตรวจที่ server (`IAuthorizationGuard`) ไม่ใช่แค่ที่ UI

**F2.4** ค่าที่ตั้งต้องมีขอบเขตที่รับได้ ปฏิเสธค่าเพี้ยนตั้งแต่ที่ server (เช่น ลิงก์หมดอายุ 0 ชั่วโมง
หรือ 100 ปี) — ตัวเลขขอบเขตจริงยังไม่เคาะ ดู OQ-4

> 🆕 **มีข้อเสนอค้างอยู่ที่จะเพิ่มค่ากลุ่มที่ 4 (บันทึก 2026-08-21 — ยังไม่ตัดสิน ไม่ใช่ส่วนหนึ่งของ
> F2 ที่เคาะแล้ว)**: ค่า pacing ของบทเรียน (`introWaitMs` / `breathPauseMs` /
> `finalQuestionWaitMs`) ซึ่งวันนี้ตั้งแยกทีละบทเรียน ให้ย้ายมาเป็นค่าเริ่มต้นระดับบริษัทที่นี่ ·
> รายละเอียดเต็ม ข้อเท็จจริงที่ตรวจกับโค้ดจริง และคำถามที่ยังไม่มีคำตอบ (P1–P4) อยู่ที่
> `_docs/module/learning-session/requirement.md` §Open Questions หัวข้อ 2026-08-21 ·
> **ถ้ารับข้อเสนอนี้ A5/B3/B4 (`design.md` §Unresolved Open Questions) ต้องขยายให้ครอบค่าพวกนี้ด้วย**
> — ห้าม implement F2 โดยคิดว่าค่านี้รวมอยู่แล้ว และห้ามตัดทิ้งโดยคิดว่าไม่มีใครขอ

### F3 · แจ้งเตือน CS — ✅ ปิดแล้ว ไม่มีงานต้องทำ

ประเด็นเดิมคือ "CS ไม่รู้ว่ามีคำถามค้างในคิว ต้องเข้ามาเช็คเอง" — ตรวจโค้ดแล้วพบว่า
**ระบบมี in-app badge อยู่แล้วจริง**: `AdminSidebar.tsx:130,142` แสดงตัวเลขสดของคิว Q&A
และคิว conflict ผ่าน `use-admin-review-counts` เจ้าของโปรเจกต์เลือกช่องทาง "in-app badge"
อย่างเดียว → requirement ข้อนี้ **ถือว่าถูกแก้ไปแล้วด้วยของที่มีอยู่ก่อนหน้า ไม่ใช่งานใหม่**

"สรุปรายวัน" ที่เคยเลือกไว้ตอนแรกถูกถอนออก เพราะขัดกันเอง — การสรุปรายวันมีความหมาย
เฉพาะเมื่อมีช่องทางที่ต้อง "ส่ง" ออกไป (อีเมล/LINE) ซึ่งไม่ได้เลือก ถ้าอนาคตอยากได้แจ้งเตือน
เชิงรุกจริง ต้องมี SMTP/LINE API ก่อน และให้เปิดเป็น requirement แยกต่างหากตอนนั้น
(ดู `## Declined / Not Pursuing` DC-1)

### F4 · การเลือก/สลับบริษัทของ owner (✅ เคาะ 2026-08-21 — change request รอบที่ 2)

ที่มา: เจ้าของโปรเจกต์ลองใช้ระบบจริงหลัง F1 ส่งมอบ แล้วเจอว่าการสลับบริษัทมี friction เกินจำเป็น
(*"จากที่ทดลองเล่นจริงเจอปัญหาแค่นี้ หลักๆ"*) — เป็นการปรับ UX ของสิ่งที่ทำไปแล้ว ไม่ใช่ฟีเจอร์ใหม่

**F4.0 — ยืนยันพฤติกรรมเดิมว่าถูกต้องแล้ว ไม่ใช่งานใหม่**: user ที่ผูกกับบริษัท (`admin`/`cs`)
ล็อกอินแล้วต้องเข้าไปอยู่ในข้อมูลบริษัทตัวเองทันทีโดยไม่ต้องเลือกอะไร — **ตรวจโค้ดแล้วทำงานถูกต้อง
อยู่แล้ว** (`AdminSessionProvider.tsx:89` fallback ไป `user.companyId`) และครอบ admin คนแรกของ
บริษัทที่สร้างใหม่ตาม F1.2 ด้วยโดยอัตโนมัติ เพราะใช้กลไกเดียวกันเป๊ะ (`ICompanyService.cs:117`
สร้าง admin คนแรกพร้อม `CompanyId` เสมอ) ไม่มีเส้นทางแยก → **ไม่มีงานต้องทำในข้อนี้**
บันทึกไว้เพื่อไม่ให้มีใครไป "แก้" สิ่งที่ถูกอยู่แล้ว

**F4.1 — owner ต้องมีช่องสลับบริษัทตลอดเวลา ไม่ผูกกับจำนวนบริษัท**: วันนี้ช่องสลับโผล่เฉพาะ
เมื่อมี 2+ บริษัท ถ้ามีบริษัทเดียวจะเป็นข้อความเฉยๆ (`CompanySwitcher.tsx:15-20`) — เปลี่ยนเป็น
dropdown เสมอสำหรับ owner ไม่ว่าจะมีกี่บริษัท

**F4.2 — เฉพาะ `owner` เท่านั้นที่เห็น dropdown** · `admin`/`cs` **คงเป็นข้อความเฉยๆ ตามเดิม**
เหตุผล: สอง role นี้ผูกกับบริษัทเดียวถาวรตาม role model (ไม่มี permission builder) — dropdown
ที่มีตัวเลือกเดียวและกดแล้วไม่เกิดอะไรคือ control หลอก และยังทำให้เข้าใจผิดว่าสลับบริษัทได้
แต่ **ห้ามซ่อนชื่อบริษัททิ้ง** เพราะจะไม่เหลือคำตอบบนจอว่า "ตอนนี้กำลังดูข้อมูลของใคร"

**F4.3 — owner ลงหน้าแรกปกติเสมอ ไม่มีขั้นตอนเลือกบริษัทคั่น**: ระบบเลือกบริษัทแรกให้อัตโนมัติ
ทุกกรณี ไม่ใช่เฉพาะตอนมีบริษัทเดียวเหมือนวันนี้ (`AdminSessionProvider.tsx:113-121`) → **จอ
"เลือกบริษัทก่อนเริ่มทำงาน" ใน `AdminGuard.tsx` ถูกยกเลิกทั้งจอ** owner สลับเองทีหลังได้ที่
dropdown ตาม F4.1 ตลอดเวลาอยู่แล้ว

**F4.4 — สร้างบริษัทใหม่ต้องไม่อยู่ใน dropdown** และไม่มีลิงก์ทางลัดไปหน้าจัดการบริษัทใน dropdown
ด้วย — การสร้าง/ปิด/เปิดบริษัทอยู่ที่ `/admin/companies` (F1.6) ที่เดียว ซึ่งจัดไว้เรียบร้อยแล้ว
และมีเมนูใน sidebar อยู่แล้ว dropdown ทำหน้าที่เดียวคือ "สลับบริษัทที่กำลังดู"

**F4.5 — บริษัทที่ปิดใช้งานแล้วไม่อยู่ใน dropdown** (พฤติกรรมเดิม ยืนยันว่าไม่เปลี่ยน) —
`GetSwitchableCompanies()` คืนเฉพาะบริษัทที่ `IsActive = true` (`ICompanyService.cs:59`)
owner ดูรายชื่อบริษัทที่ปิดแล้วได้ที่ `/admin/companies` แต่สลับเข้าไปดูข้อมูลข้างในไม่ได้

**F4.6 — บริษัทที่กำลังดูอยู่ถูกปิดใช้งานกลางคัน**: ให้สลับไปบริษัทที่ยัง active ตัวแรกอัตโนมัติ
ไม่ต้องมีจอคั่นบอกว่า "บริษัทนี้ถูกปิดแล้ว" — ให้สอดคล้องกับ F4.3 ที่ยึดหลัก "ไม่มีขั้นตอนคั่น"
(เคสนี้เกิดจริงได้: owner อยู่ที่ `?company=scb` แล้วกดปิด `scb` เองที่ `/admin/companies`
ทำให้ค่าใน URL ชี้ไปบริษัทที่หายจากรายการแล้ว)

## Scope

### MVP (must-have)

เรียงตามลำดับที่เคาะไว้ — **สร้างบริษัทใหม่ก่อน แล้วค่อยตั้งค่าระดับบริษัท**:

1. F1 ทั้งหมด (F1.1–F1.6) — สร้างบริษัทใหม่แบบฟอร์มเดียวจบ + หน้ารายการบริษัท
2. F2 ทั้งหมด (F2.1–F2.4) — ตั้งค่า 3 ข้อ พร้อมรูปแบบ inherit
3. **F4 ทั้งหมด (F4.1–F4.6)** — UX สลับบริษัทของ owner (เพิ่ม 2026-08-21 หลัง F1 ส่งมอบแล้ว) ·
   เป็นงาน **frontend อย่างเดียว ไม่แตะ schema/endpoint/ตรรกะสิทธิ์ใดๆ** (F4.5 ยืนยันว่าใช้
   พฤติกรรม server เดิม) · F4.0 ไม่มีงานต้องทำ เป็นการยืนยันของเดิม

### รอบปิด scope — ยืนยันแล้ว 2026-08-21 ว่าไม่อยู่ในโมดูลนี้

ถามครบตามขั้นตอนปิด scope ก่อนส่งต่อ `system-analyst` แล้ว ทั้งสามข้อเป็นการตัดสินใจของ
เจ้าของโปรเจกต์ ไม่ใช่ประเด็นที่ยังไม่ได้ถาม:

1. **หน้าจัดการ `AdminUser` เต็มรูปแบบต่อบริษัท** (เพิ่ม/ปิด/รีเซ็ตรหัสผ่าน admin/cs รายอื่น) —
   **ไม่ทำใหม่** โมดูลนี้สร้างแค่ admin **คนแรก** ตอนสร้างบริษัทเท่านั้น ที่เหลือใช้หน้า
   `/admin/users` เดิมที่มีอยู่แล้ว
2. **แพ็กเกจ / โควตา / วันหมดอายุสัญญา / หน้า usage ต่อบริษัท** — **ยังไม่คิดตอนนี้ และห้าม
   ออกแบบเผื่อ** ดูความเสี่ยงที่ยอมรับแล้วใน `## Constraints & Assumptions`
3. **หน้าแสดง audit log ของการสร้าง/ปิดบริษัท** — ยังไม่ต้องมี (ดู Later ข้างบน)

## Constraints & Assumptions

- **ไม่มีระบบส่งอีเมลในระบบนี้เลย** (grep ทั้ง repo แล้วไม่เจอโค้ดอีเมลใดๆ) — ทุกอย่างที่ออกแบบ
  ในโมดูลนี้ต้องทำงานได้โดยไม่พึ่งอีเมล รวมถึงการส่งมอบรหัสผ่านให้ admin คนแรก (ดู OQ-1)
- **`Company.Id` เป็น slug ที่คนตั้ง ไม่ใช่ id ที่ generate** และมันโผล่ใน URL admin
  (`?company=scb`) จึงติดอยู่ใน browser history / server log / referrer header — ห้ามใส่อะไร
  ที่เป็นความลับ (ตาม comment ใน `Company.cs:17-22`) และเปลี่ยนทีหลังแทบไม่ได้เพราะเป็น
  primary key ที่ทุกตารางอ้างถึง
- **`Company` และ `AdminUser` ไม่มี query filter โดยตั้งใจ** — สองตารางนี้เป็น tenant registry
  เอง การใส่ filter จะทำให้ switcher ไม่มีอะไรให้สลับและ owner (`CompanyId = null`) ล็อกอินไม่ได้
  → ทุก query ต้อง scope ตัวเองและ `IAuthorizationGuard` คือสิ่งเดียวที่กั้นข้อมูลข้ามลูกค้า (TD-014)
  งานในโมดูลนี้แตะสองตารางนี้โดยตรง จึงเป็นจุดที่ security ต้องดูเป็นพิเศษ
- **ผู้เรียนไม่มีบัญชีและจะไม่มีตลอดไป** (ตาม `AdminUser.cs:6-9`) — แบรนด์ที่ผู้เรียนเห็นใน F2.1
  จึงต้องเสิร์ฟให้คนที่ไม่ได้ล็อกอินได้ โดยผูกกับ token ของลิงก์ ไม่ใช่ session ของ admin
- **Edge TTS ไม่เหมาะกับ production อยู่แล้ว** (TD-001, `CLAUDE.md` §Known Baseline) — การทำ
  UI เลือกเสียงต่อบริษัทตอนนี้จึงต้องออกแบบไม่ให้ผูกตายกับ Edge TTS จนย้าย provider แล้วต้องรื้อ
- Provider ทั้งหมด (`SLIDES_PROVIDER`, `KNOWLEDGE_PROVIDER`, ฯลฯ) **ยังเป็นค่าระดับ deployment
  เหมือนเดิม ไม่ใช่ค่าต่อบริษัท** — ไม่มีในสโคปนี้และไม่ใช่สิ่งที่ตกหล่น
- ทั้ง 3 ค่าใน F2.1 เป็นการตัดสินใจของเจ้าของโปรเจกต์เองล้วนๆ ไม่ได้อ้างอิงข้อมูลภายนอกใดๆ
  จึงไม่มีแถวใน `## References` (ตารางว่างโดยถูกต้อง ไม่ใช่ตกหล่น)
- **ความเสี่ยงที่ยอมรับแล้ว (ยืนยัน 2026-08-21)**: เรื่องแพ็กเกจ/โควตา/วันหมดอายุสัญญา/หน้า usage
  ต่อบริษัท **ยังไม่คิดในรอบนี้ และห้ามออกแบบเผื่อ** เจ้าของโปรเจกต์รับทราบแล้วว่าถ้าอนาคตต้องมี
  จะต้องกลับมาแตะตาราง `Company` ซ้ำอีกรอบ และยอมรับความเสี่ยงนั้น — บันทึกไว้เพื่อให้
  `system-analyst` ไม่ต้องยกประเด็นนี้ขึ้นมาใหม่ราวกับยังไม่มีใครถาม และเพื่อไม่ให้มีใครแอบใส่
  ฟิลด์เผื่ออนาคตลง Data Model โดยอ้างว่า "เดี๋ยวก็ต้องใช้"
- **มี `SeedFirstCompanyHostedService` แล้ว (เพิ่ม 2026-08-21)** — สร้างบริษัทตั้งต้นหนึ่งแถว
  ("School Bright", id `schoolbright`) ตอน startup **เฉพาะเมื่อตาราง `Company` ว่างสนิท** ตาม
  รูปแบบเดียวกับ `SeedFirstOwnerHostedService` เดิม ปรับได้ด้วย env `FIRST_COMPANY_ID` /
  `FIRST_COMPANY_NAME` · **ค่า default นี้ต้องถูกเปลี่ยนก่อนนำ codebase ไปใช้นอก deployment จริง
  ของ School Bright** — เจ้าของโปรเจกต์วางแผน fork ไปทำวิทยานิพนธ์ และไม่ต้องการให้ชื่อ
  "School Bright" ติดไปกับสำเนานั้น
- **⚠️ ความเสี่ยงที่ยอมรับแล้ว (ยืนยันสองครั้ง 2026-08-21) — สถานะ 0 บริษัทจะไม่มี UI รองรับเลย**:
  F4.3 ยกเลิกจอ "เลือกบริษัทก่อนเริ่มทำงาน" และ **จอ "ยังไม่มีบริษัทในระบบ" ก็ถูกยกเลิกด้วย**
  (จอหลังนี้เพิ่งถูกเพิ่มเข้ามาวันเดียวกันแล้วถอดออกในรอบเดียวกัน) · เจ้าของโปรเจกต์ยืนยันซ้ำหลัง
  ได้ฟังความเสี่ยงแบบเจาะจงแล้วว่า *"ยืนยันเอาออก - ยอมรับความเสี่ยงนั้น"*
  **ความเสี่ยงที่ยอมรับคืออะไรกันแน่**: `SeedFirstCompanyHostedService` ทำงานเฉพาะตอนตาราง
  **ว่างสนิท** เท่านั้น ถ้าวันหนึ่ง owner ปิดใช้งานบริษัททุกแห่ง จำนวนบริษัท *active* จะเป็น 0
  แต่ตารางไม่ว่าง → seed ไม่ทำงาน → ไม่มี dropdown ให้เลือก (F4.5 ตัด inactive ออก) และไม่มีจอไหน
  บอก owner ว่าทำไมหน้าจอโหลดไม่ขึ้น · ผลที่ตามมาซึ่งยอมรับแล้วเช่นกัน: หน้าที่ scope ตามบริษัท
  จะยิง request ที่ล้มเหลวด้วย "company unknown" ตรงตามที่ comment เดิมใน `AdminGuard.tsx:52-56`
  เตือนไว้เอง · ทางออกในสถานการณ์นั้นคือเข้า `/admin/companies` ตรงๆ (owner-only page ที่ยกเว้น
  จาก gate) แล้วเปิดใช้งานบริษัทกลับคืน
  **บันทึกไว้ชัดเพราะนี่คือการตัดสินใจโดยเจตนา ไม่ใช่สิ่งที่ตกหล่น** — ห้าม `system-analyst`
  หรือ `security` ยกขึ้นมาใหม่ราวกับยังไม่มีใครถาม และห้ามใครแอบใส่จอกลับเข้าไปโดยไม่ถามเจ้าของ
- **ไม่สร้างหน้าจัดการผู้ใช้ใหม่**: การเพิ่ม/ปิด/รีเซ็ตรหัสผ่าน admin กับ cs รายอื่นใช้หน้า
  `/admin/users` เดิมที่มีอยู่แล้ว โมดูลนี้แตะ `AdminUser` เฉพาะจุดเดียวคือการสร้าง admin
  **คนแรก** พร้อมบริษัทใน F1.2
