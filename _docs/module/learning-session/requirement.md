## Overview

`sb_supportroom` คือห้องเรียนสาธิตด้วยเสียงสำหรับทีม CS ของ School Bright ใช้สอนคุณครูให้ใช้งาน
ระบบเองโดยไม่ต้องมีคนนั่งประกบ

**เหตุผลตั้งต้นของทั้งโมดูล — คำอธิบาย use case จริงจากเจ้าของโปรเจกต์:**

> **ลิงก์ = สื่อการสอน** ที่ส่งลงกลุ่มไลน์ได้ ใครก็หยิบไปใช้ได้จนกว่าจะหมดอายุ
> **ห้องเรียนเกิดขึ้นตอนที่ผู้ใช้กดเข้าและระบุชื่อตัวเอง** — แต่ละคนเรียนแบบตัวใครตัวมัน 1:1
> ไม่ใช่ห้องประชุมที่ทุกคนอยู่ด้วยกัน

โครงสร้างวันนี้ผูก **1 ลิงก์ = 1 การเรียน** เป็นก้อนเดียวกัน ซึ่งไม่รองรับ use case ข้างบน
การเปลี่ยนแปลงหลักของโมดูลนี้จึงคือ **แยก "ลิงก์" ออกจาก "การเรียน" เป็นสองสิ่ง** —
ลิงก์หนึ่งอันมีการเรียนได้หลายรายการ แต่ละรายการเป็นของคนละคน (และคนเดิมเรียนซ้ำได้หลายรอบ)
สถานะ/ความคืบหน้าเป็นของ *การเรียน* ไม่ใช่ของ *ลิงก์*

บนฐานนั้น โมดูลนี้เพิ่ม:

1. **ผู้เรียนกรอกชื่อตัวเองก่อนเข้าห้อง** (แบบ Zoom) แทนที่ CS จะกรอกให้ล่วงหน้าตอนสร้างลิงก์
2. **บันทึกความคืบหน้า** ทุกครั้งที่เปลี่ยนสไลด์ เพื่อกลับมาเรียนต่อได้ และให้ CS เห็นว่าถึงสไลด์ไหน
3. **แยก "ดูครบทุกสไลด์" ออกจาก "จบแล้ว"** เพราะผู้เรียนกดจบเองกลางคันได้
4. **CS รีวิวคำตอบ AI ว่าถูก/ผิด พร้อมหมายเหตุ** เพื่อรู้ว่าต้องแก้ที่คลังความรู้ ที่ RAG หรือที่ prompt
5. **หน้าสรุปสองมุม** — ผู้เรียนเห็นเฉพาะคำถาม-คำตอบของตัวเอง · CS เห็นเต็มรวมจุดที่ AI ตอบไม่ได้

ผู้ได้ประโยชน์: ทีม CS (แจกลิงก์เดียวลงกลุ่ม แล้วยังรู้ว่าใครเรียนถึงไหน ถามอะไร AI ตอบผิดตรงไหน)
และคุณครู/ผู้เรียนปลายทาง (หยิบลิงก์ในกลุ่มมาเรียนเมื่อไหร่ก็ได้ · ปิดแท็บแล้วกลับมาเรียนต่อจากจุดเดิม)

## Target Users & Roles

| บทบาท | ใครคือใคร | ทำอะไรได้ |
|---|---|---|
| CS (หลังบ้าน) | ทีม Customer Success ของ School Bright | สร้าง/จัดการลิงก์ (หนึ่งลิงก์แจกได้หลายคน) · ดูรายการ **การเรียนทุกรายการที่เกิดใต้ลิงก์นั้น** · ดูสรุปเต็มรายการเรียน · รีวิวคำตอบ AI ว่าถูก/ผิด + เขียนหมายเหตุ |
| ผู้เรียน | คุณครู/พนักงานปลายทางที่หยิบลิงก์จากกลุ่มไลน์ | เปิดลิงก์ · กรอกชื่อตัวเอง · เรียนแบบตัวใครตัวมัน · ถามคำถาม · กดจบเอง · กด "เรียนอีกครั้ง" · ดูสรุปคำถาม-คำตอบ **ของการเรียนตัวเองเท่านั้น** |

**ไม่ได้แก้เรื่อง auth** แต่ทำให้ขอบเขต "ข้อมูลใครเห็นได้บ้าง" ชัดขึ้น — ดู Constraints

## Core Features

### F1 — "ลิงก์" กับ "การเรียน" เป็นคนละสิ่ง (การเปลี่ยนแปลงหลัก)

```
เดิม (โค้ดวันนี้)   1 ลิงก์ = 1 การเรียน          ผูกติดกันเป็นก้อนเดียว
ใหม่                1 ลิงก์ = หลายการเรียน แยกคนละคน
```

**ลิงก์** คือสื่อการสอนที่ส่งลงกลุ่มไลน์ได้ ใครก็หยิบไปใช้ได้จนกว่าจะหมดอายุ
**การเรียน** เกิดขึ้นตอนที่ผู้ใช้กดเข้าและระบุชื่อตัวเอง — หนึ่งรายการต่อหนึ่งคนหนึ่งรอบ

CS กรอกตอนสร้างลิงก์: **บทเรียน** · **หน่วยงาน** (ไม่บังคับ) · **วันหมดอายุ** ·
**จำนวนคนสูงสุดต่อลิงก์** (ไม่บังคับ — ดู F8)
CS **ไม่กรอกชื่อผู้เรียนอีกต่อไป** — ผู้เรียนกรอกเองตอนเข้าห้อง (F2)

- "หน่วยงาน" เป็นคำกลางที่ครอบทั้งโรงเรียน สาขาธนาคาร และแผนกในบริษัท
  placeholder ที่เคาะไว้: `เช่น โรงเรียนวัดโพธิ์ / สาขาสีลม / ฝ่ายบุคคล`
- label "หน่วยงาน" มีแค่ CS เห็น ผู้เรียนเห็นเฉพาะ *ค่า* ที่ CS พิมพ์ จึงยังไม่ต้องตั้งค่าต่อบริษัท
- **ลิงก์หมดอายุระหว่างมีคนเรียนค้างอยู่ → ให้การเรียนที่ค้างอยู่ทุกรายการดำเนินต่อจนจบ ไม่ตัดกลางคัน**
  แต่หลังหมดอายุแล้วจะ *เริ่ม* การเรียนใหม่บนลิงก์นั้นไม่ได้ (เคาะ 2026-08-18)
- **ข้อมูลที่เป็นของลิงก์**: บทเรียนที่ผูก · หน่วยงาน · วันหมดอายุ · จำนวนคนสูงสุด ·
  บริษัทเจ้าของ (ตามแบบแผน multi-company เดิม) · audit ผู้สร้าง/เวลาสร้าง
- **ข้อมูลที่ต้องย้ายออกจากลิงก์ไปเป็นของการเรียน**: ชื่อผู้เรียน · สถานะ · เวลาเริ่ม/เวลาจบ ·
  ดูครบทุกสไลด์ · สไลด์ล่าสุด — วันนี้ทั้งหมดนี้อยู่บน `TrainingSession` ซึ่งจะกลายเป็น "ลิงก์"
  (สเปกเดิม §3.1) เก็บไว้ที่เดิมไม่ได้ เพราะลิงก์เดียวมีได้หลายคน หลายสถานะ หลายความคืบหน้าพร้อมกัน

### F1b — ตาราง "การเรียนของแต่ละคน" (ตารางใหม่)

ต้องมีที่เก็บใหม่หนึ่งชุดต่อ "การเรียนหนึ่งรอบของหนึ่งคน" (สเปกเดิม §3.2) —
**นี่คือของใหม่ที่ยังไม่มีในโค้ดวันนี้เลย** และเป็นหัวใจของโมดูล

เหตุผลที่ต้องเป็นตารางใหม่ ไม่ใช่เพิ่มคอลัมน์บนของเดิม: จำนวนการเรียนต่อลิงก์ไม่จำกัดและไม่รู้ล่วงหน้า
คนหนึ่งคนยังเรียนซ้ำได้หลายรอบ (F5) — โครงสร้างแถวเดียวต่อลิงก์รองรับไม่ได้ทั้งสองข้อ

ข้อมูลที่กติกาต้องเก็บได้ต่อการเรียนหนึ่งรายการ:

| เก็บอะไร | ทำไม |
|---|---|
| ลิงก์ที่ใช้เข้ามา | ผูกกลับไปหาบทเรียน/หน่วยงาน/วันหมดอายุ |
| บริษัทเจ้าของ | แบบแผน multi-company เดิม ต้องมี query filter |
| กุญแจผู้เรียน (`LearnerKey`) | แยกคน + กลับมาเรียนต่อ — ดู F3 |
| ชื่อผู้เรียน | ผู้เรียนกรอกเอง (F2) |
| สถานะ (กำลังเรียน / จบแล้ว) | CS ดูภาพรวมได้ |
| เวลาเริ่ม · เวลาจบ | ลำดับเวลา + ใช้แยกรายการที่ชื่อซ้ำกัน |
| เวลาที่มีความเคลื่อนไหวล่าสุด | F6 ใช้คำนวณ "หยุดกลางคัน" |
| สไลด์ล่าสุด (id) + ลำดับที่ของสไลด์ | กลับมาเรียนต่อ (F3) + แสดง "7/20" (F4) |
| ดูครบทุกสไลด์แล้วหรือยัง | แยกจาก "จบแล้ว" ตาม F5 |
| audit ผู้สร้าง/เวลาสร้าง | ตามแบบแผนเดิมของโปรเจกต์ |

### F2 — ผู้เรียนกรอกชื่อตัวเองก่อนเข้าห้อง

เปิดลิงก์ → หน้ากรอกชื่อ → กดเข้า → เริ่มเรียน

- **กรอกชื่ออย่างเดียว ไม่เอาเบอร์โทร อีเมล หรือตำแหน่ง** — ตั้งใจเลี่ยงข้อมูลส่วนบุคคล
  (เคาะ 2026-08-18) ผลที่ตามมา: เฟสนี้ **ไม่ต้องติด 🔒 Security gate ด้วยเหตุผลเรื่อง PII**
- **นี่คือการย้ายจุดกรอก ไม่ใช่การเพิ่มฟิลด์ใหม่ล้วนๆ** — วันนี้ชื่อผู้เรียนถูกกรอกโดย *คนสร้างลิงก์*
  (ดูคอมเมนต์บน `RecipientName` ใน `TrainingSession.cs`: "Free text typed by whoever created
  the session") เฟสนี้เปลี่ยนให้ **ผู้เรียนเป็นคนกรอกเอง** ตอนเข้าห้อง และค่าไปอยู่ที่
  *การเรียน* ไม่ใช่ที่ *ลิงก์* (F1) — ลิงก์เดียวมีได้หลายชื่อ
- ชื่อยังคงเป็น **ป้ายกำกับ ไม่ใช่การยืนยันตัวตน** ตามเดิม — ไม่มีการตรวจสอบว่าเป็นคนนั้นจริง
- **กดเข้า = สร้างการเรียนรายการใหม่** หนึ่งแถวต่อหนึ่งคนหนึ่งรอบ

### F3 — กุญแจผู้เรียนทำสองหน้าที่

ระบบเก็บ **กุญแจผู้เรียน (`LearnerKey`)** ไว้ที่ browser ของผู้เรียนตอนเข้าห้อง (สเปกเดิม §2.4)
กุญแจนี้ทำ **สองหน้าที่พร้อมกัน** — ขาดข้อใดข้อหนึ่งไม่ได้:

1. **กลับมาเรียนต่อ** — เน็ตหลุด ปิดแท็บ ปิดคอม แล้วเปิดลิงก์เดิมบนเครื่อง/เบราว์เซอร์เดิม
   → กลับไปยังการเรียนรายการเดิมได้ **หลังยืนยันตัวตนหนึ่งครั้ง** (ดูกติกาข้างล่าง)
   ไม่ต้องกรอกชื่อใหม่ถ้ายืนยันว่าเป็นคนเดิม
2. **แยกว่าใครเป็นใครบนลิงก์เดียวกัน** — **คนที่สองที่เปิดลิงก์เดิมต้องไม่เห็นของคนแรก**
   ทั้งความคืบหน้าและคำถาม-คำตอบ · ลิงก์เป็นของกลางที่แจกในกลุ่มไลน์ จึงใช้ตัวลิงก์เอง
   เป็นตัวตัดสินว่าใครเป็นใครไม่ได้

**สองกรณีนี้เป็นคนละเรื่องกัน อย่าอ่านปนกัน** — ต่างกันที่ "มีกุญแจอยู่หรือไม่":

#### กรณี ก — ไม่มีกุญแจเลย (ล้าง browser storage / เปลี่ยนเครื่อง / เปิดคนละเบราว์เซอร์)

ระบบไม่มีอะไรให้ผูกกลับ → **กลายเป็น "คนใหม่"** (เคาะ 2026-08-18 — คำตอบ Q6 เดิม ยังคงเดิม)

- ผู้เรียนจะเริ่มการเรียนรอบใหม่จากศูนย์ กรอกชื่อใหม่ ไม่ได้ต่อของเดิม — **ยอมรับได้
  ไม่ต้องทำอะไรเพิ่มในเฟสนี้**
- ผลข้างเคียงที่ยอมรับแล้วเช่นกัน: ฝั่ง CS จะเห็นเป็นสองรายการที่แยกไม่ออกว่าเป็นคนเดียวกัน
  เหมือนกรณี **คนละคนแต่ชื่อซ้ำกัน** บนลิงก์เดียวกัน
- เหตุผล: กรณีนี้เกิดไม่บ่อย · CS อ่านจากเวลา/ความคืบหน้าแทนได้ · และตรงกับหลัก
  "อย่าสร้าง infrastructure ล่วงหน้า" ของโปรเจกต์

#### กรณี ข — มีกุญแจ และเจอการเรียนที่ยังไม่จบผูกอยู่กับกุญแจนี้บนลิงก์นี้

**ต้องถามยืนยันก่อนเสมอ ห้ามพาเข้าไปเรียนต่อเงียบๆ** (เคาะ 2026-08-18)

- แสดงคำถามทำนอง **"คุณคือ *(ชื่อที่บันทึกไว้)* ใช่ไหม"** พร้อมทางเลือกสองทาง:
  - **ใช่** → เข้าไปเรียนต่อจากสไลด์เดิมของการเรียนรายการนั้น
  - **เริ่มเรียนใหม่ในชื่ออื่น** → ไปหน้ากรอกชื่อ (F2) แล้วสร้างการเรียน**รายการใหม่**
    รายการเดิมไม่ถูกลบ ไม่ถูกเขียนทับ และคำถามใหม่ต้องไม่ไปกองรวมกับของรายการเดิม
- **เหตุผลที่ต้องถาม อย่า "ปรับปรุง" ให้กลับไป resume เงียบๆ:** กุญแจอยู่ที่ *เบราว์เซอร์*
  ไม่ใช่ที่ *คน* — บนเครื่องที่ใช้ร่วมกัน (คอมกลางในโรงเรียน ห้องสมุด) คนละคนใช้กุญแจตัวเดียวกัน
  ถ้า resume เงียบๆ คนที่สองจะถูกพาเข้าไปเรียนต่อของคนแรก **เห็นความคืบหน้าและคำถามของคนแรก**
  และคำถามใหม่จะไปกองรวมกับของคนแรกในรายงานที่ CS อ่าน
- **ต้นทุนที่ยอมรับแล้ว:** ผู้เรียนคนเดิมต้องกดยืนยันเพิ่มหนึ่งครั้งทุกครั้งที่กลับเข้ามาหลังเน็ตหลุด/ปิดแท็บ
- เลือกวิธีนี้เพราะแก้ปัญหาเครื่องใช้ร่วมกันได้โดย **ไม่ต้องเพิ่ม login/OTP หรือระบบระบุตัวตนใดๆ** —
  **อย่าเสนอ login/OTP/รหัสยืนยันในเฟสนี้** (ยังคงเป็นข้อห้ามเดิม)
- ยังเป็นไปตาม F2: ชื่อคือ **ป้ายกำกับ ไม่ใช่การยืนยันตัวตน** — การกดยืนยันนี้คือการให้ผู้ใช้
  *เลือกเอง* ว่าจะเรียนต่อหรือเริ่มใหม่ ไม่ใช่การพิสูจน์ตัวตน

### F4 — บันทึกความคืบหน้าล่าสุด

ทุกครั้งที่เปลี่ยนสไลด์ ระบบอัปเดต **ความคืบหน้าล่าสุดของการเรียนรายการนั้น** (อัปเดตแถวเดิม
ไม่สร้างแถวใหม่ต่อสไลด์) — ความคืบหน้าเป็นของ *การเรียน* ไม่ใช่ของ *ลิงก์*

- ต้องเก็บได้พอที่จะ (ก) พาผู้เรียนกลับไปยังสไลด์เดิม และ (ข) แสดงเป็นตัวเลข "7/20" ให้ CS เห็น
  โดยไม่ต้องไป resolve deck ใหม่ (วันนี้เก็บแค่ id ของสไลด์ ยังไม่มีลำดับที่)
- ต้องเก็บ **เวลาที่มีความเคลื่อนไหวล่าสุด** เพราะ F6 ใช้คำนวณ (ยังไม่มีในโครงสร้างวันนี้)

### F5 — "เรียนจบ" นับสองค่าแยกกัน + หน้าสรุป

**"เรียนจบ" เกิดได้สองทาง: ดูครบทุกสไลด์ หรือผู้เรียนกดปุ่มจบเอง** (เคาะ 2026-08-18)
จึงต้องเก็บ **สองค่าแยกจากกัน** ห้ามยุบเป็นค่าเดียว:

| ค่า | ความหมาย |
|---|---|
| ดูครบทุกสไลด์แล้วหรือยัง | ผู้เรียนไปถึงสไลด์สุดท้ายจริงไหม |
| จบแล้วหรือยัง (+ เวลาที่จบ) | การเรียนนี้ปิดแล้วไหม ไม่ว่าจะครบสไลด์หรือไม่ |

เหตุผล: CS ต้องแยกออกว่าใคร "กดจบกลางคัน" (จบแล้ว แต่ไม่ครบสไลด์) ซึ่งเป็นสัญญาณคนละแบบกับคนที่เรียนครบ

หน้าสรุปมองได้สองมุม:

| ใคร | เห็นอะไร |
|---|---|
| ผู้เรียน | "เรียนจบแล้ว" + **คำถาม-คำตอบของการเรียนตัวเอง** + ปุ่ม **"เรียนอีกครั้ง"** |
| CS (หลังบ้าน) | สรุปเต็มของการเรียนรายการนั้น: คำถามทั้งหมด · จุดที่ AI ตอบไม่ได้ · ช่องรีวิว |

กติกาสำคัญ: ผู้เรียน **ไม่เห็น** รายการ "จุดที่ AI ตอบไม่ได้ รอ CS ตรวจสอบ" — เป็นข้อมูลภายในของ CS
"จุดที่ตอบไม่ได้" ไม่ต้องเก็บซ้ำ — คำนวณจากคำถามที่ AI รายงานว่าไม่พบข้อมูล (`not_found`) ได้อยู่แล้ว

**ปุ่ม "เรียนอีกครั้ง" = สร้างการเรียนรอบใหม่** (สเปกเดิม §2.5) — คนหนึ่งคนมีได้หลายรอบบนลิงก์เดียวกัน
รอบเก่าไม่ถูกลบหรือเขียนทับ CS ยังเห็นทุกรอบ · **"จบแล้ว" ไม่ได้แปลว่าจบถาวร**

### F6 — "หยุดกลางคัน" คิดตอนแสดงผล ไม่เก็บเป็นสถานะ

ไม่มีสถานะ "หยุดกลางคัน" ในฐานข้อมูล แต่คำนวณตอนแสดงผล:

```
(ตอนนี้ - เวลาที่มีความเคลื่อนไหวล่าสุด) > INACTIVE_THRESHOLD_MINUTES  →  แสดงว่า "หยุดกลางคัน"
```

- ค่าเริ่มต้น **30 นาที** ปรับผ่าน env ตามแบบแผนเดิมของโปรเจกต์ (`ServerDefaults.cs`)
- เหตุผลที่ไม่ให้ browser ส่งสัญญาณตอนปิดแท็บ: สัญญาณนั้นพลาดบ่อย (ปิดคอม เน็ตหลุด แบตหมด =
  ไม่มีสัญญาณ) และเปลี่ยนใจทีหลังไม่มีต้นทุน เพราะไม่ได้เก็บลง DB

### F7 — CS รีวิวคำตอบ AI (ถูก/ผิด + หมายเหตุ)

CS ทำเครื่องหมาย **ถูก/ผิด** ต่อคำถามหนึ่งข้อ และเขียน **หมายเหตุแบบข้อความอิสระ** (ไม่บังคับ)

เหตุผลที่ต้องมีช่องหมายเหตุ — "ตอบผิด" มีได้อย่างน้อย 3 สาเหตุที่แก้คนละทางกัน:

1. คลังความรู้ไม่มีข้อมูลนี้จริง → เพิ่มเอกสาร
2. มีข้อมูลอยู่ แต่ค้นหาไม่เจอ → ปรับ RAG (threshold / chunk)
3. AI เดาเอง ตอบจากความรู้ทั่วไป → แก้ prompt

ถ้าเก็บแค่ถูก/ผิดจะแยกไม่ออก แล้วมักจบลงที่ "เพิ่มเอกสาร" ทั้งที่ปัญหาจริงคือข้อ 3
เลือก **ช่องข้อความอิสระแทน enum โดยตั้งใจ** เพราะยังไม่รู้ว่าจะเจอสาเหตุแบบไหนอีกบ้าง —
อย่าเปลี่ยนเป็น dropdown/enum ในเฟสนี้

ข้อมูลที่กติกาต้องเก็บได้ต่อคำถาม: ผลรีวิว (ถูก/ผิด/ยังไม่รีวิว) · หมายเหตุ (ว่างได้) · เวลาที่รีวิว (ว่างได้)

**คำถามและบทสนทนาต้องผูกกับ "การเรียน" แทน "ลิงก์"** (สเปกเดิม §3.3, §3.4) — วันนี้ผูกกับลิงก์
ซึ่งใช้ไม่ได้เมื่อลิงก์เดียวมีหลายคน คำถามของคนที่สองจะไปปนกับของคนแรก และหน้าสรุปฝั่งผู้เรียน
(F5) จะรั่วข้ามคน

### F8 — ช่อง "จำนวนคนสูงสุดต่อลิงก์" (กรอกได้ แต่ยังไม่บังคับใช้)

**โชว์ช่องให้ CS กรอกได้ตอนสร้างลิงก์ แต่ระบบยังไม่บังคับใช้ในเฟสนี้** (เคาะ 2026-08-18)

- ว่างไว้ = ไม่จำกัด
- **ต้องมีข้อความกำกับใน UI ว่าค่านี้ยังไม่มีผล** เพื่อไม่ให้ CS เข้าใจผิดว่าระบบกันคนเกินให้แล้ว
- เหตุผลที่เตรียมที่เก็บไว้ก่อน: เพิ่ม *คอลัมน์* ทีหลังเจ็บกว่าเตรียมไว้ตั้งแต่แรก และค่าที่ CS
  กรอกไว้จะใช้ได้ทันทีเมื่อวันหนึ่งเปิดการบังคับใช้
- **การ *บังคับใช้* ยังคงถูกตัดออกตามมติ 2026-08-11** — ดู `## Declined / Not Pursuing`

### F9 — ฝั่งผู้เรียนต้องใช้งานได้ครบบนมือถือ/แท็บเล็ต (responsive แบบคิดทุก interaction)

**เคาะแล้ว 2026-08-22 จากการสัมภาษณ์เจ้าของโปรเจกต์ (R1–R6)** — ไม่ใช่งานจัด CSS ให้พอดีจอ
แต่คือการไล่ว่า *ทุก interaction* ที่ทำได้บน desktop ทำงานยังไงบนจอสัมผัส

- **อุปกรณ์เป้าหมาย (R1): desktop เป็นหลัก แต่มือถือ/แท็บเล็ตต้องทำงานได้ครบ** — **ไม่ใช่
  mobile-first** · desktop ยังเป็นประสบการณ์หลักที่ออกแบบรอบตัวมัน มือถือ/แท็บเล็ตคือ
  "ต้องใช้ได้ครบ" ไม่ใช่ "ต้องดีที่สุด"
- **ขอบเขต (R2): ฝั่งผู้เรียนอย่างเดียว** — `/room/*` และ `/join/*` · **ไม่รวม `/admin/*`
  ของ CS** (ยืนยันแล้วว่าตั้งใจไม่เอาหลังบ้านในรอบนี้)
- **ยอมให้บาง interaction ไม่รองรับมือถือได้ไหม (R4): ไม่ได้ — ต้องครบทุกอย่าง ไม่มีข้อยกเว้น**
  ทุกการทำงานฝั่งผู้เรียนต้องใช้ได้บนจอเล็ก ห้ามยกอะไรไปเป็น "desktop only"
- **จอแนวตั้ง (R5): ต้องใช้งานได้เต็มรูปแบบในแนวตั้ง (portrait) — ห้ามบังคับหมุนจอ**
  (ห้ามใช้หน้าจอ "กรุณาหมุนเป็นแนวนอน" เป็นทางออก แม้สไลด์จะเป็นเนื้อหาแนวนอนโดยธรรมชาติ)
- **จังหวะงาน (R6): ดึงเข้าชุดที่กำลังส่ง UX/UI อยู่ตอนนี้เลย** — ไม่ใช่รอบแยกทีหลัง
  (กลับคำจากบริบทเดิมที่เคย "กันฝั่งผู้เรียนออกจากรอบนั้นไปก่อน")

**กติกาต่อ interaction ที่เคาะแล้ว (R3):**

| interaction | กติกาบนจอเล็ก |
|---|---|
| Push-to-talk (R3a) | **กดค้างเหมือนเดิม** ไม่เปลี่ยนเป็นกดครั้งเดียวสลับเปิด/ปิด · แต่ **ต้องกันไม่ให้หน้าเลื่อน (scroll) และไม่ให้เด้ง context menu ระหว่างกดค้าง** |
| ดูสไลด์ (R3b) | **แตะเพื่อขยายสไลด์เต็มจอ (fullscreen) ได้** |
| แชต (R3c) | เป็น **drawer เต็มจอ เปิด-ปิดได้ ไม่แย่งพื้นที่สไลด์** · ⚠️ ดูหมายเหตุใต้ตาราง |
| ปุ่มจบ/ออก (R3c) | **เข้าถึงได้ตลอดเวลา ไม่ต้องเลื่อนหา** |
| แป้นพิมพ์เด้งขึ้น (R3c) | **ต้องไม่บังช่องพิมพ์และปุ่มส่ง** |
| รายการสไลด์/ความคืบหน้า (R3c) | **ย่อเป็นแถบบาง หรือซ่อนไว้ใต้ปุ่ม** |

> ⚠️ **หมายเหตุถึง `system-analyst` (บันทึก 2026-08-22 ตอนปิด T4-a):** แถว "แชต (R3c)" ถูกตอบไว้
> ตอนที่ยังมีแชตคุยกับ CS อยู่ · เมื่อ T4-a ตัดแชต CS ออกทั้งฟีเจอร์ (ดู F10) **สิ่งที่ยังต้องเป็น
> drawer เต็มจอบนจอเล็กคือช่องสนทนากับ AI ช่องเดียวที่เหลือ** — กติกา "เต็มจอ เปิด-ปิดได้
> ไม่แย่งพื้นที่สไลด์" ยังมีผลบังคับตามเดิม เปลี่ยนแค่ปลายทางของข้อความ **ไม่ใช่การเพิกถอน R3c**

### F10 — พิมพ์ถามแทนการพูด (เทียบเท่าการพูด 100%)

**เคาะแล้ว 2026-08-22 จากการสัมภาษณ์เจ้าของโปรเจกต์ (T1–T7)** — เหตุผลตั้งต้นคือ
"ต้องมี User ที่ไม่สะดวกพูดถามตลอด" ซึ่งเป็น use case ของตัวเอง ไม่ใช่แค่ทางออกของมือถือ

- **สถานะของฟีเจอร์ (T1): เทียบเท่าการพูด 100%** — พิมพ์ถามแล้วทำได้ทุกอย่างที่ถามด้วยเสียงทำได้
  ไม่ใช่ทางสำรองที่จำกัดกว่า
- **การบันทึกและคิวรีวิว (T2): คำถามที่พิมพ์ต้องถูกบันทึกและเข้าคิวรีวิวเหมือนกันทุกประการ
  กับคำถามที่พูด** — เข้าหน้าสรุป F5 และคิวรีวิวถูก/ผิดของ CS ตาม F7 เหมือนกัน ·
  ⚠️ **ผลที่ตามมา: งานนี้แตะโครงสร้าง `SessionQuestion` และคิวรีวิว F7 จริง ไม่ใช่งาน UI ล้วน**
- **เสียงอ่านคำตอบ (T3): อ่านออกเสียง (TTS) เหมือนเดิมทุกครั้ง** — **ไม่มีโหมดเงียบ**
  แม้คำถามจะถูกพิมพ์เข้ามาก็ตาม
- **จังหวะหยุดการบรรยาย (T5): บรรยายต่อไปจนกว่าจะกดส่ง แล้วค่อยหยุด** — **ไม่ interrupt
  ทันทีที่โฟกัสช่องพิมพ์** ซึ่งต่างจาก push-to-talk ที่ interrupt ตั้งแต่กดค้าง ·
  จุดตัดคือ "กดส่ง" ไม่ใช่ "เริ่มพิมพ์"
- **การตอบ readiness (T6): ไม่รองรับการพิมพ์ตอบ** — ให้เปลี่ยนจุดนี้เป็น
  **ปุ่มกด "พร้อม" / "ยังไม่พร้อม" แทนไปเลย** ไม่ต้องพิมพ์และไม่ต้องพูด
- **ลำดับงาน (T7): ทำพร้อมกับงาน responsive (F9) ชุดนี้เลย** ไม่ใช่เฟสถัดไป
- **ช่อง input (T4 + T4-a): ✅ ปิดสมบูรณ์แล้ว 2026-08-22** — **รวมเป็นช่องเดียว โดยเปลี่ยน
  พฤติกรรมของช่องเดิม** — **ไม่ใช่**สร้างช่องพิมพ์ถาม AI ช่องใหม่แยกจากช่องแชตใน `ChatDrawer`
  และ **ไม่ใช่**ทำให้ช่องเดิมฉลาดขึ้นแล้วแยกปลายทางเอง · **ช่องพิมพ์เดียวในห้องเรียนต่อจากนี้
  มีปลายทางเดียวคือ AI เท่านั้น** ตรงกับ T1–T7 ที่เคาะไปแล้ว
- **ตัดแชตคุยกับเจ้าหน้าที่ CS ระหว่างเรียนออกจากขอบเขตทั้งหมด (T4-a — ✅ เคาะแล้ว 2026-08-22):**
  ฟีเจอร์แชตข้อความระหว่างคน (ผู้เรียน ↔ CS ผ่าน SignalR `SendChatMessage`) **ถูกตัดออกทั้งฟีเจอร์
  ไม่ใช่แค่ซ่อน UI** · **ไม่มีทางสำรองอื่นให้ผู้เรียนคุยกับคนจริงระหว่างเรียน** — ระหว่างอยู่ในห้อง
  ผู้เรียนคุยได้กับ AI อย่างเดียว · เจ้าของโปรเจกต์เลือกทางเลือกที่ 1 จากสามทางที่เสนอ
  (ตัดทิ้งจริง / ย้ายไปที่อื่น / ไม่จำเป็นอยู่แล้ว) และยืนยันซ้ำ 2 รอบในแชท

## Constraints & Assumptions

- **ไม่ใช่โปรเจกต์ใหม่** — ต่อยอดจากระบบที่ deploy โค้ดจริงอยู่แล้ว (`frontend/` Next.js 15 +
  `backend/` ASP.NET Core .NET 10 + EF Core/PostgreSQL) การเปลี่ยน schema ต้องผ่าน EF Core migration ใหม่
  ตามกฎใน root `CLAUDE.md` — **ไม่ใช่ Prisma** แม้ pipeline default จะพูดถึง `schema.prisma`
- แบบแผน multi-company เดิมต้องคงไว้: ข้อมูลทุกชิ้นของโมดูลนี้ผูกกับบริษัท และต้องกรองด้วย query filter
- ค่า threshold ปรับผ่าน env ตามแบบแผน `ServerDefaults.cs` ของโปรเจกต์ ไม่ hardcode
- **ยังไม่มี auth ในระบบ (TD-002)** — โมดูลนี้ไม่ได้แก้เรื่องนั้น ข้อมูลที่เพิ่มเข้ามาไม่มีข้อมูล
  ส่วนบุคคล (ชื่ออย่างเดียว ตาม F2) แต่ยังมี **หมายเหตุรีวิวภายในของ CS** ที่ไม่ควรเปิดสาธารณะ
  และ `/admin/*` ยังเปิดอยู่ — ให้ `system-analyst`/`project-manager` ชั่งว่าจะติด 🔒 Security gate
  ด้วยเหตุนี้หรือไม่ **แต่ไม่ใช่ด้วยเหตุผลเรื่อง PII ซึ่งถูกตัดออกไปแล้วโดยตั้งใจ**
- ตัดสินใจโดยตั้งใจ (อย่าเสนอเปลี่ยนโดยไม่ amend เอกสารนี้ก่อน):
  - **1 ลิงก์ = หลายการเรียน แยกคนละคน** ตามสเปกเดิม §1 — ยืนยันซ้ำเมื่อ 2026-08-18
    หลังเคยพลิกเป็น 1:1 แล้วเพิกถอนในวันเดียวกัน
  - ลิงก์เป็นสื่อการสอนของกลาง แจกในกลุ่มไลน์ได้ · การเรียนเกิดตอนกดเข้า+ระบุชื่อ
  - `LearnerKey` ใน browser คือตัวแยกคนบนลิงก์เดียวกัน (F3) — ล้าง storage/เปลี่ยนเครื่อง =
    กลายเป็นคนใหม่ ยอมรับแล้ว รวมถึงกรณีที่ CS แยกสองรายการไม่ออก (เหมือนกรณีชื่อซ้ำ)
  - **มีกุญแจแล้วเจอการเรียนค้างอยู่ = ต้องถามยืนยันก่อนเสมอ ห้าม resume เงียบๆ** (F3 กรณี ข) —
    เพราะกุญแจอยู่ที่เบราว์เซอร์ ไม่ใช่ที่คน และเครื่องกลางในโรงเรียน/ห้องสมุดถูกใช้ร่วมกัน ·
    ต้นทุน = กดยืนยันเพิ่มหนึ่งครั้งตอนกลับเข้ามา ยอมรับแล้ว · ห้ามแก้เป็น login/OTP
  - "หยุดกลางคัน" คำนวณตอนแสดงผล ไม่เก็บสถานะลง DB
  - "ครบทุกสไลด์" กับ "จบแล้ว" เป็นคนละค่า ห้ามยุบรวม
  - หมายเหตุรีวิวเป็นข้อความอิสระ ไม่ใช่ enum/dropdown
  - "จุดที่ AI ตอบไม่ได้" ไม่เก็บซ้ำ คำนวณจาก `AnswerStatus = not_found`
  - **ระหว่างอยู่ในห้องเรียน ผู้เรียนคุยได้กับ AI อย่างเดียว ไม่มีช่องทางคุยกับคนจริงเลย**
    (T4-a, 2026-08-22) — ถามทวนแล้วว่านี่แปลว่าตัดฟีเจอร์แชตคุยกับ CS ทิ้งจริงหรือไม่
    เจ้าของโปรเจกต์ยืนยันว่า **ตั้งใจ** · ผลที่รับไว้แล้ว: เมื่อ AI ตอบ `not_found` หรือผู้เรียนติดขัด
    **ไม่มีทางขอความช่วยเหลือจากคนระหว่างเรียน** — ใช้เส้นทางเดิมนอกระบบ (ไลน์/โทรหา CS) แทน
    และ CS เห็นปัญหาย้อนหลังผ่านคิวรีวิว F7 · ⛔ `system-analyst`/`qa-engineer` **ไม่ต้องยกขึ้นมา
    ถามซ้ำ** ว่าควรมี fallback ให้คุยกับคนไหม — ถามและตอบไปแล้ว

โปรเจกต์ · ยืนยันแล้วว่าช่องว่างนี้มีจริงและยังไม่มีใครแก้)**

2. **`TranscriptionFailed` ถูกใช้ซ้อนสองความหมายอยู่แล้ว** —

   ยุบเป็น label/badge เดียวกัน ("ถอดเสียงไม่ได้") ที่ CS เห็นแยกไม่ออก
3. **ความล้มเหลวเชิงเทคนิคไม่เคยถูกเขียนลง DB เลย** —
   `VoiceQuestionService.AskAsync`/`AskTextAsync`
   (`backend/src/SupportRoom.Application/Services/IVoiceQuestionService.cs:79-152`)
   เขียนแถว `SessionQuestion` **เฉพาะเมื่อ provider คืนค่าสำเร็จโดยไม่ throw** · exception
   ทุกแบบ (Gemini timeout/429 หลัง retry 3 ครั้ง · `GEMINI_API_KEY` หายผ่าน

   `tutor-reducer.ts:293-300` / `config/response-texts.ts:10-11`:
