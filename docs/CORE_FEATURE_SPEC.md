## 1. การเปลี่ยนแปลงหลัก: แยก "ลิงก์" ออกจาก "การเรียน"

```
เดิม   1 ลิงก์ = 1 การเรียน            ผูกติดกันเป็นก้อนเดียว
ใหม่   1 ลิงก์ = หลายการเรียน แยกคนละคน
```

เหตุผล: ลิงก์หนึ่งอันส่งให้หลายคนได้จนกว่าจะหมดอายุ แต่ละคนเรียนของตัวเอง 1:1
(ห้องเรียน ไม่ใช่ห้องประชุม) — สถานะและความคืบหน้าจึงเป็นของแต่ละคน ไม่ใช่ของลิงก์

**ห้องกลุ่มในอนาคต** = สร้างเป็นลิงก์คนละชนิด แยกจากของเดิม ไม่ยัดเข้ามาในนี้

## 2. Flow ที่ตกลงกัน

### 2.1 CS สร้างลิงก์

CS กรอก: บทเรียน · **หน่วยงาน** (ไม่บังคับ) · วันหมดอายุ
CS **ไม่กรอกชื่อผู้เรียนอีกต่อไป**

คำว่า "หน่วยงาน" เป็นคำกลางที่ครอบทั้งโรงเรียน สาขาธนาคาร และแผนกในบริษัท
placeholder: `เช่น โรงเรียนวัดโพธิ์ / สาขาสีลม / ฝ่ายบุคคล`

> label นี้มีแค่ CS เห็น — ผู้เรียนเห็นเฉพาะ *ค่า* ที่ CS พิมพ์ จึงไม่ต้องตั้งค่าต่อบริษัท
> ถ้าวันหนึ่งอยากให้ตั้งค่าได้ ค่อยเพิ่มตอนทำ auth (ตอนนั้นตาราง `Company` ต้องมีอยู่แล้ว)

### 2.2 ผู้ใช้เปิดลิงก์

**ผู้ใช้กรอกชื่อตัวเองก่อนเข้าห้อง** (ล้อกับ Zoom) — ไม่ใช่ CS กรอกให้

เมื่อกดเข้า ระบบสร้างแถว "การเรียน" ใหม่ และเก็บ key ไว้ใน browser ของผู้ใช้

### 2.3 ระหว่างเรียน

บันทึก **ความคืบหน้าล่าสุด** ทุกครั้งที่เปลี่ยนสไลด์ (อัปเดตแถวเดิม ไม่สร้างแถวใหม่)

> ยังไม่ทำ event log ต่อสไลด์ — การเพิ่ม *ตาราง* ใหม่ทีหลังไม่เจ็บ ต่างจากการเพิ่ม *คอลัมน์*
> ถ้าวันหนึ่งอยากได้ dashboard ว่าคนหลุดที่สไลด์ไหน ค่อยเพิ่มตอนนั้น

### 2.4 เน็ตหลุด / ปิดแท็บ แล้วกลับมา

จำผ่าน **browser storage** — กลับเข้ามาเรียนต่อจากสไลด์เดิมได้ ไม่ต้องกรอกอะไรใหม่

browser key ทำสองหน้าที่พร้อมกัน:
1. กลับมาเรียนต่อได้
2. แยกว่าใครเป็นใครบนลิงก์เดียวกัน — คนที่สองเปิดลิงก์เดิมต้องไม่เห็นของคนแรก

### 2.5 เรียนจบ / เปิดลิงก์ซ้ำ

| ใคร | เห็นอะไร |
|---|---|
| ผู้เรียน | "เรียนจบแล้ว" + **คำถาม-คำตอบของตัวเอง** + ปุ่ม `เรียนอีกครั้ง` |
| CS (หลังบ้าน) | สรุปเต็ม: คำถามทั้งหมด · จุดที่ AI ตอบไม่ได้ · ช่องรีวิว |

ผู้เรียน **ไม่เห็น** "จุดที่ตอบไม่ได้ รอ CS ตรวจสอบ" — เป็นข้อมูลภายใน
กด `เรียนอีกครั้ง` = สร้างการเรียนรอบใหม่ (คนหนึ่งคนมีได้หลายรอบ)

### 2.6 หยุดกลางคัน

ไม่เก็บเป็นสถานะในฐานข้อมูล แต่ **คำนวณตอนแสดงผล**

```
(ตอนนี้ - เวลาล่าสุด) > INACTIVE_THRESHOLD_MINUTES  →  แสดงว่า "หยุดกลางคัน"
```

ค่าเริ่มต้น **30 นาที** ปรับผ่าน env ตามแบบแผนเดิมของโปรเจกต์ (`ServerDefaults.cs`)

> เลือกวิธีคำนวณแทนการให้ browser ส่งสัญญาณตอนปิดแท็บ เพราะสัญญาณนั้นพลาดบ่อย
> (ปิดคอม เน็ตหลุด แบตหมด = ไม่มีสัญญาณ) และเพราะเปลี่ยนใจทีหลังไม่มีต้นทุน

### 2.7 CS รีวิวคำตอบ AI

CS ทำเครื่องหมาย **ถูก/ผิด** + เขียน **หมายเหตุ** (ไม่บังคับ)

เหตุผลที่ต้องมีช่องหมายเหตุ — "ตอบผิด" มีได้ 3 สาเหตุที่แก้คนละทางกัน:

```
1. คลังความรู้ไม่มีข้อมูลนี้จริง   →  เพิ่มเอกสาร
2. มีข้อมูลอยู่ แต่ค้นหาไม่เจอ    →  ปรับ RAG (threshold / chunk)
3. AI เดาเอง ตอบจากความรู้ทั่วไป  →  แก้ prompt
```

ถ้าเก็บแค่ถูก/ผิดจะแยกไม่ออก แล้วมักจบลงที่ "เพิ่มเอกสาร" ทั้งที่ปัญหาจริงคือข้อ 3
เลือกช่องข้อความอิสระแทน enum เพราะยังไม่รู้ว่าจะเจอสาเหตุแบบไหนอีกบ้าง

**ยังไม่ทำ** สถานะ "จัดการแล้ว" — ถ้าวันหนึ่งรายการกองจน CS สับสน ค่อยเพิ่ม

## 3. Schema ที่จะได้

### 3.1 `TrainingSession` → **`TrainingLink`** (rename)

```
คงไว้    Id · CompanyId · Token · LessonId · LessonSlug · ExpiresAt
         RecipientOrgName        ← หน่วยงาน CS กรอก
         CreateBy/CreateDate/... ← audit ที่มีอยู่แล้ว

เพิ่ม    MaxAttendees int?       ← null = ไม่จำกัด (ยังไม่ใช้ในเฟสนี้)

ย้ายออก  RecipientName · Status · StartedAt · EndedAt
         CompletedAllSlides · LastSlideObjectId
```

**rename เพราะความหมายของแถวกลับด้าน** — วันนี้ 1 แถว = การเรียนของคน 1 คน
หลังแยกแล้ว 1 แถว = ลิงก์ที่หลายคนใช้ร่วมกัน ชื่อคลาสเดิมจะหมายถึงคนละอย่างกับเมื่อวาน

ผลพลอยได้ที่ใหญ่กว่านั้น: พอคำว่า "Session" หายไปจากฝั่งลิงก์
`SessionQuestion.SessionId` · `ChatMessage.SessionId` · route `api/session-questions`
**ไม่ต้องเปลี่ยนชื่อเลย** — แค่เปลี่ยน FK ให้ชี้ `LearningSession` แล้วชื่อพวกนี้กลับมา*ถูก*
(คำถาม/แชตเป็นของ "การเรียน" อยู่แล้วโดยธรรมชาติ)

ถ้าคงชื่อเดิมไว้จะได้ระบบที่ `SessionQuestion.SessionId` ชี้ไปตารางที่ไม่ได้ชื่อ Session
ส่วนตารางที่ชื่อ Session กลับไม่ใช่ตัวที่มันชี้ — และ `GetBySessionId()` ที่มีอยู่ 4–5 ที่
จะอ่านแล้วตอบไม่ได้ว่า session ไหน ตลอดไป

route `api/sessions` → `api/training-links` ไปด้วย (ยังไม่มีผู้ใช้ภายนอก)
และหน้า `/admin/sessions` → `/admin/links`

### 3.2 ตารางใหม่ **`LearningSession`** — การเรียนของแต่ละคน

```
Id
CompanyId              ← ตามแบบแผน multi-company (ต้องมี query filter ด้วย)
TrainingLinkId         ← ลิงก์ที่ใช้เข้ามา
LearnerKey             ← key ที่ browser เก็บ ใช้แยกคนบนลิงก์เดียวกัน + กลับมาเรียนต่อ
RecipientName          ← ผู้ใช้กรอกเอง
Status                 ← IN_PROGRESS | ENDED
StartedAt / EndedAt
LastActivityAt         ← ใช้คำนวณ "หยุดกลางคัน"
LastSlideObjectId      ← กลับมาเรียนต่อจากตรงนี้
LastSlideIndex         ← แสดง "7/20" ได้โดยไม่ต้อง resolve deck ใหม่
CompletedAllSlides
CreateBy/CreateDate/...
```

### 3.3 `SessionQuestion`

```
เปลี่ยน  ผูกกับ "การเรียน" แทน "ลิงก์"
เพิ่ม    ReviewResult   ← "correct" | "incorrect" | null (ยังไม่รีวิว)
         ReviewNote     ← text ว่างได้
         ReviewedAt     ← ว่างได้
```

### 3.4 `ChatMessage`

```
เปลี่ยน  ผูกกับ "การเรียน" แทน "ลิงก์"
```

### 3.5 `SessionSummary` — **ลบทิ้ง** คำนวณสดตอนอ่านแทน

ตารางนี้เก็บ 3 อย่าง ซึ่งหลังแยกโครงสร้างแล้วซ้ำซ้อนทั้งหมด:

| เก็บอะไร | หลังแยกแล้ว |
|---|---|
| `CompletedAllSlides` | ย้ายไปอยู่ที่ `LearningSession` → **มี 2 ที่เก็บความจริงเดียวกัน** |
| `LastSlideObjectId` | เหมือนกันเป๊ะ |
| `UnansweredPoints` | derived — คำนวณจาก `SessionQuestion` ที่ `AnswerStatus = not_found` ได้ |

เหตุผลเดียวที่ปกติจะเก็บ snapshot ไว้คือ "อยากได้ภาพ ณ เวลานั้น แช่แข็งไม่เปลี่ยน"
**แต่โค้ดนี้ไม่ได้ทำแบบนั้นอยู่แล้ว** — comment ในไฟล์เขียนเองว่ารายการคำถามไม่ได้ copy เก็บ
แล้ว `GetBySessionId` ก็ join สดจาก `SessionQuestion` ตอนอ่าน → ได้ของครึ่งแช่แข็งครึ่งสด
ซึ่งแย่กว่าทั้งสองแบบ

ฟีเจอร์รีวิว (§2.7) ทำให้มันผิดหนักขึ้น: CS จะแก้ `ReviewResult`/`ReviewNote` บน
`SessionQuestion` *หลัง*เรียนจบ แต่ `UnansweredPoints` แช่แข็งไว้ตั้งแต่วินาทีที่จบ
นานไปสองอันจะเล่าเรื่องไม่ตรงกัน แล้วไม่มีใครรู้ว่าอันไหนถูก

```
ลบ    entity + ตาราง + ISessionSummaryRepository + ISessionSummaryService
คงไว้  SessionSummaryViewModel  ← เปลี่ยนจาก "อ่านจากตาราง" เป็น "คำนวณสด"
                                  frontend กับ api-client.ts ไม่ต้องแก้
```

### 5.1 หน้า join — กรอกชื่ออย่างเดียว

```
        [ ชื่อบทเรียน ]

  ชื่อของคุณ
  ┌──────────────────────────┐
  │                          │   ← ช่องเดียว required, trim, ≤100 ตัว
  └──────────────────────────┘

       [  เข้าห้องเรียน  ]
```

ลง DB แค่ `RecipientName` = ค่าที่พิมพ์ · `LearnerKey` = key ที่ browser สร้างเอง

**ไม่เก็บ**: อีเมล · เบอร์โทร · โรงเรียน/สาขา (CS กรอกที่ `RecipientOrgName` ตอนสร้างลิงก์แล้ว)
· รหัสพนักงาน · ตำแหน่ง — เป็น PII ที่ยังไม่มี flow ไหนใช้

**ครั้งที่สองเป็นต้นไป**: มี `LearnerKey` ใน browser storage แล้ว → **ข้ามหน้านี้ทั้งหน้า**
เข้าห้องต่อจากสไลด์เดิมทันที ไม่ถามชื่อซ้ำ

ที่ตามมาโดยอัตโนมัติ: ชื่อซ้ำกันได้ (ตัวแยกคนคือ `LearnerKey` ไม่ใช่ชื่อ) และชื่อไม่ใช่ตัวตน
— ตรงกับ comment ที่มีอยู่แล้วบน `RecipientName` ว่า *"not an identity, not authentication"*

## 6. ที่ตัดออกโดยตั้งใจ (อย่าเผลอทำ)

| สิ่งที่ตัด | เหตุผล |
|---|---|
| Event log ต่อสไลด์ | เพิ่มตารางทีหลังไม่เจ็บ ยังไม่มีคนใช้ข้อมูลนี้ |
| สถานะ "จัดการแล้ว" ในการรีวิว | รอจนรายการกองจนสับสนก่อน |

| จำกัดจำนวนคนต่อลิงก์ | ใส่คอลัมน์ไว้ก่อน แต่ยังไม่บังคับใช้ |
| ห้องกลุ่ม | เป็นฟีเจอร์ใหม่ ลิงก์คนละชนิด |
